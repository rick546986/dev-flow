① 零到一 checklist

這章要你懂:裝機只有五件事,而且只有第 3 件真的要你動腦 —— 其餘四件都是打一行、看它回報。勾一勾記錄進度(存在本機瀏覽器)。

  • 0. 剛裝好或剛改過 plugin → 打 /reload-plugins
  • 1. cd 進新專案 repo root → 打 dev-setup(不帶參數)
  • 2. 看它建了什麼,並回應兩個徵你同意的動作
  • 3. 逐條核可 .claude/rules/arch-invariants.md 草稿 ← 唯一要動腦的一步
  • 4. 收下 check 的固定四段回報,確認沒有異常項

0. plugin 已改過就先 reload

跟 AI 說 如果你剛裝好、或剛改過 dev-talk/dev-flow plugin, 在當前 session 打:

/reload-plugins

為何:skills 與 hooks 隨 plugin 全域生效(安裝目錄 ~/.claude/plugins/cache/dev-flow/dev-flow/<version>/,Windows 對應 %USERPROFILE%\.claude\plugins\cache\dev-flow\dev-flow\<version>\; dev-talk 已併入同一 plugin,單一正本),但執行中的 session 不會自動感知改動,要 reload 新版 skill/hook 才生效(見 dev-setup SKILL「注意」節)。

1. 進專案打 dev-setup(不需參數)

跟 AI 說 cd 進新專案 repo root 後:

dev-setup

它會自動偵測現況分流,不用你自己判斷裝過沒:

綠 = 全新安裝、黃 = 要你先看 diff、紅 = 有異常待修。四條路都以 check 收尾。

偵測狀態動作
無 docs/dev/fresh跑 install,完成後跑 check 回報
有 docs/dev/,但版本落後母版stale先列 diff 摘要徵同意 → upgrade → check
有且與母版一致current只跑 check
check 抓到異常broken列異常+修法,徵得同意後 fix

明講子命令(dev-setup check / upgrade / install / fix / uninstall)會跳過偵測,直接照該子命令走。

2. install 完成後,它建了什麼(fresh 情境)

  • docs/dev/README.md ← cp 母版 ~/dev/dev-flow/README.md
  • docs/dev/_templates/ ← cp 母版 _templates/
  • docs/dev/STATUS.md ← 從模板建(進行中 feature 看板)
  • repo root CONTEXT.md ← 若無則從模板建(詞彙表)
  • .claude/rules/arch-invariants.md —— 自動產草稿(不是空殼):收割使用者指名的 external workflow artifacts 與 CLAUDE.md 的技術規則段 → 派 sonnet 掃 codebase 抓候選 → 每條標 【待確認】 列給你逐條核可,見下一步
  • .gitignore 加一行 .devflow/(執行守衛的狀態檔目錄)
  • docs/dev/devflow-contract.json ← cp 母版正本(版本握手契約; devflow-exec.sh doctor 無明示指定時在此找契約,缺件必 fail-closed)
  • docs/dev/tools/devflow-evidence-gauntlet.sh ← cp 母版 scripts/ 並 chmod +x(Stage 7 Evidence 機械檢查 E1–E13;散發後跑兩道可執行驗證)

兩個會跳出來徵你同意的動作,不是自動靜默完成:

  • 文檔歸位:專案裡若有散落文件,會提議 git mv 進 docs/specs/ / docs/dev/ / docs/adr/,並同步全部引用(README §1)
  • 外部 workflow artifacts:使用者指名後,只讀取其中可重用的「架構不變量/ 技術慣例」作為 rules 草稿候選;未指名目錄不掃描,原 artifacts 不移動、不覆蓋、不刪除

專案若已有其他 external workflow artifacts 與目錄,一律保留不動; dev-setup 不轉換也不接管它們。

3. 核可 .claude/rules/arch-invariants.md 草稿

install 會產草稿,你要做的是逐條核可(不是從零寫)。草稿每條長這樣:

## 交易與併發
- 【待確認】寫入路徑一律走 TxManager(可設 isolation level + idempotent retry),
  禁直接開 tx  <- 證據:internal/db/tx_manager.go:42;信心:高

核可 = 拿掉 【待確認】;不同意就刪。留著標記的條目不得被當事實引用。 判準兩問:①這條錯了會出 bug 或被 review 打回嗎?②新 session 看檔案結構會知道嗎? ①是 ②否 → 留。

七類骨架(模板已列)內容範例
資料層軟刪除一律 deleted_at,查詢預設帶 WHERE deleted_at IS NULL; pg unique violation(23505)必攔截轉 domain error
交易與併發寫入走 TxManager(isolation level + 指數退避 retry 上限 5 次),禁直接開 tx
錯誤處理domain error 定義位置;API 層才轉 HTTP status,domain 層不碰 HTTP
分層與依賴方向業務規則只住 domain/services/,API 層禁寫業務 if/else;依賴方向 api → application → domain
命名與慣例DB 欄位 snake_case、struct tag 對映、測試檔命名
已知地雷(最高價值)踩過的坑,例:某 cache 需在某動作後手動失效,否則會用到舊資料 —— 這種別人絕對看不出來
驗證指令cd backend && PYTHONPATH=. python -m pytest tests/、npm run build
放什麼不放什麼
架構不變量與 gotchas —— 光看 repo 看不出來、會讓人踩坑的事 (例:「某張表禁止直接寫,一定要走某個 service」) dev-flow 流程規則(README/gate/lane 那套)—— 這檔案每 session 自動注入, 寫進流程規則等於把「有這套 SOP」的知識灌給所有 agent,包含理應對下游盲的 /dev-talk (README §11:「禁把流程規則寫進專案 CLAUDE.md/AGENTS.md」)
spec 內容 —— living spec 已經在 docs/specs/,不重抄
「看 repo 就知道的事」—— 那是雜訊,不是不變量

4. check 的固定回報格式

不論走哪個分流(fresh/stale/current/broken),結尾回報都是固定四段:

  1. 判定狀態一句
  2. 做了什麼(逐條)
  3. check 結果表
  4. 還需要你決定的事(可空)

check 項目數與編號以 skills/dev-setup/SKILL.md 的 check 節為準 (JSON/掛載/自測/盲掃/專案面…),其中第 9 項驗 gauntlet 散發(存在、與母版無 diff、兩道可執行驗證),第 10 項驗版本握手: docs/dev/devflow-contract.json 與母版無 diff,且 devflow-exec.sh doctor 可執行並看 verdict —— 報 INCOMPATIBLE 是刻意 fail-closed,不得繞過或改綠。

Stage 6 三步順序為何不可調

正確順序:先進工作樹 → devflow-exec.sh start → status 核對 → dev-run。 完整可複製指令(單線用 feature branch,多 feature 並行用 worktree 互不干擾):

# 單線(不需要 cd,已經在這棵樹上):
git checkout -b feature/<slug>

# 並行(多 feature 互不干擾,建完務必 cd 進去):
git worktree add -b feature/<slug> <path>
cd <path>

# 兩者接下來都一樣(PLUGIN = 安裝路徑,版號依安裝而定,見 docs/PLUGIN.md;
# Windows 對應 %USERPROFILE%\.claude\plugins\cache\dev-flow\dev-flow\<version>):
PLUGIN=~/.claude/plugins/cache/dev-flow/dev-flow/<version>
"$PLUGIN/hooks/devflow-exec.sh" start <slug>
"$PLUGIN/hooks/devflow-exec.sh" status  # 核對 slug 與 cwd 相符

跟 AI 說 dev-run <slug> 才是最後一步。dev-run SKILL 原文:

守衛只武裝「start 當下所在的那棵樹」—— 先 start 再換樹 = 安全網失效。

原因是 git worktree 各自有獨立的 git-dir(.git/worktrees/<name>), 守衛的 sentinel 檔案與 .devflow/exec.json 的 baseline/scope 都是對「start 當下的 cwd」算出來的。 在主樹 start 完再 cd 進 worktree,武裝的是錯的樹,新樹完全不設防。 status 這一步不是可省的裝飾 —— 就是拿來核對「slug 與 cwd 相符」,提早抓到樹選錯的情況。

為什麼 start 是分界點(生命週期因果):start 之前, .devflow/exec.json 不存在 —— 每次工具呼叫,掛在 PreToolUse 的 devflow-guard.sh/devflow-prebash.sh 讀狀態時拿到「未武裝」,對 Read 與 Bash 一律靜默放行,完全無感;唯一的例外訊號是 A-7 軟提醒 —— 且範圍很窄:只在 Write/Edit 打中 5-tasks/6-implementation-notes 時才響,而且整個 repo 只響一次(git-dir sentinel 記過就不再提醒,不是持續警告)。start 把 baseline/scope/契約 hash 寫進 .devflow/exec.json 之後,PreToolUse 才有 依據可比對、可擋 —— 這就是三步順序不可調的生命週期理由:沒有步驟 2(start), 之後每一次 PreToolUse 都無米可炊,擋不了任何東西。

Stage 7 的 G3 + Exit checklist

G3 PASS 之後,7-review.md 的 Exit Checklist 要全勾才算 shipped:

規則正本 · Exit Checklist(逐字抄自 _templates/7-review.md)

  • [ ] Design Boundary finding 全數處置(契約 applicable 時必勾;n-a 時記 n-a): 未經授權的 Boundary 變更不論 🔴 或 🟡 都不得帶著出貨 —— 逐條落在下列三種之一: ①已修正(diff 已回到契約內);②記 L2 回 G2 改契約後重審; ③Owner 明示接受或 park:寫下 owner、理由、追蹤位置 (STATUS 待辦或 7-review known limits,擇一,須寫得出實際落點)。 無記錄的 🟡 = 未處置,不得勾。理由:PASS 門檻只寫「無 🔴」, 而未授權 Boundary 變更的預設分級是 🟡 —— 沒有這一條它就會靜默出貨 (2026-08 fresh review F-5)
  • [ ] Quiz(不可逆改動必做;其餘 full lane 選配,fast 免):AI 就本次變更出 3-5 題考 approver(改了什麼/為何/邊界),全對才准 merge
  • [ ] (條件式)整合回歸:跑 docs/dev/tools/devflow-integration-regression.sh --integration origin/<整合分支> --fork-sha <6-notes 步 0 記的 FORK_INTEGRATION_SHA> (整合分支 = develop 或 main,依專案;工具自己會 fetch;工作樹必須乾淨, 否則它 exit 2 擋你)。⚠️ 一定要在動樹之前跑 —— 順序寫死為 「跑腳本算交集 → 合併 → 跑全套測試」,不是「合併 → 測試 → 算交集」: 合併之後 HEAD 已含對方內容、merge-base 也已漂移,兩個座標都被污染, 那時算出來的「沒有共同戰場」是假的。依腳本印出的 STATUS 決定: · N_A_NO_INCOMING → 記 n-a 即勾(分岔後對方零新 commit) · SYNC_REQUIRED_NO_OVERLAP → 合併它印的 INTEGRATION_SHA + 跑全套測試,做完才可勾 · SYNC_REQUIRED_WITH_OVERLAP → 上面兩件 + 共同戰場交集逐檔看過,做完才可勾 · ALREADY_SYNCED → 你已經合過了,這次輸出不算數:交集必須在動樹之前算, 拿同步後的輸出當證據就是上面說的那個假綠 勾的時候把腳本最後一行的結論貼進本檔(含三個 SHA 與 canonical ref)。 ⚠️ 合併時合的是腳本印出的 INTEGRATION_SHA,不是 branch 名 —— branch 名 會跑,中間別人再合進來,你實際併進來的內容跟剛才檢查過的就不是同一份。 ⚠️ 動手合併之前無條件再跑一次腳本(不是「隔了一段時間才跑」—— 那是 主觀條件,人一定會說服自己「應該還好」):兩次的 STATUS 與座標必須完全 相同才准動手;有任何一項不同 → 停下,照新的重算
  • [ ] PR → develop(feature branch,禁直上 master)
  • [ ] 4-spec delta 已併入 docs/specs/<domain>.md
  • [ ] STATUS.md 已更新為 shipped(這一步在整合分支上、PR 合併後由合併那個 PR 的人 做,不塞進本 branch 的 PR —— 動線與理由見 STATUS 模板頂註)

③ 執行守衛速查表

這是 guide-dev-flow.html ⑥ 的同一張圖,放在這裡讓你先看到 「被擋下時你人在生命週期哪裡」的整體地圖;三走廊(左掛靠/中主幹/右 dev-flow 掛鉤)、範圍框與顏色語意的完整解說、 以及下面「你看到的訊息 ⇒ 是哪支 hook」速查表,都以 guide-dev-flow ⑥ 為準。

這章要你懂:你被擋的時候,一定是 Claude agent 生命週期的 PreToolUse 或 PostToolUse 這兩格在擋你 —— 知道是哪一格,就知道是「動手前擋下來」還是「動完了事後才查到」; 剩下唯一要你判斷的是 L1 還是 L2,判不出來時規則已經幫你決定了(當 L2)。

Claude agent 一輪的生命週期(站數以 guide-dev-flow ⑥ 的圖為準):
SessionStart(hooks 註冊/skills 描述進場)→ UserPromptSubmit(/指令展開)→ PreToolUse(寫入前擋)→ 工具執行 → PostToolUse(事後偵測)→ Stop → 壓縮 → SessionEnd。
dev-flow 的守衛逐字以 hooks/hooks.json 為準,只掛在其中兩格: PreToolUse = devflow-guard(Edit|Write|Read)+ history-guard(Edit|Write)+ devflow-prebash(Bash)+ devflow-dispatch-guard(Task|Agent); PostToolUse = devtalk-guard(Edit|Write)+ devflow-postbash(Bash)。換句話說:被 dev-flow 擋,必是這兩格之一 —— 別處(SessionStart 只是 hook 註冊/skills 描述進場,Stop/壓縮/SessionEnd) 不會是原因。機制細節(誠實界線、fail-closed 語意、逐 hook 攻防表)見 guide-dev-flow.html ⑥。

Stage 6 的守衛本體是 devflow-exec.sh(plugin hooks 內,無 alias,要打路徑; 安裝路徑 ~/.claude/plugins/cache/dev-flow/dev-flow/<version>/, Windows 對應 %USERPROFILE%\.claude\plugins\cache\dev-flow\dev-flow\<version>\):

~/.claude/plugins/cache/dev-flow/dev-flow/<version>/hooks/devflow-exec.sh start <slug>

此檔已可執行(chmod +x 免打),下文一律省略路徑,單寫 devflow-exec.sh。

startdevflow-exec.sh start <slug> 依序檢查:①本工作樹是否已武裝 —— 武裝中他模組 start 一律拒絕 (不靜默覆寫;見下方「並行與多模組」),同模組重跑 = re-arm 允許 (5-tasks 改動後重釘 scope 的正常路徑);②驗 4-spec 存在且 status: approved; ③逐 T 驗 Covers/Files/Verify/Blocked-by;④把 Git repository root 相對的 Files 聯集 正規化成 scope。scope 外的真實髒檔會拒絕 start(先 commit/還原/ 換乾淨 worktree),不會被收進 baseline;唯一例外:.gitignore 若與 HEAD 的 差異只有上次 start 自己 append 的 .devflow/ 一行,視為良性,不擋 re-arm。 全部通過後才記錄 scope 內 baseline、契約 hash、寫 sentinel。

並行與多模組:守衛的邊界在「工作樹」

  • 守衛狀態(.devflow/exec.json + git-dir sentinel)以當前工作樹為 單位,一個工作樹同一時間只武裝一個模組。
  • 多模組並行的正解:各開 git worktree。每個 worktree 有自己的 toplevel 與 git-dir,守衛 state 天然隔離 —— 模組 A 在 worktree 甲跑 Stage 6 時,模組 B 在 worktree 乙 寫 spec、跑自己的 Stage 6,互不阻擋。模組 A 在 task 執行、模組 B 已進後段 stage 的 混速並行,就用這個方式。
  • 同一工作樹內硬要並行做不到,且是刻意設計:hooks 分不清寫入來自哪個 session,武裝期間跨 feature 的 1/2/3/4 契約檔一律保護(fail-closed)。
  • 武裝中另一模組 start → 拒絕並提示開 worktree 或先 stop;絕不靜默覆寫已武裝模組的 scope/baseline(舊版曾有此漏洞,已修並入 selftest)。

紅虛線是隔離面:一個工作樹同一時間只武裝一個模組,而每個 worktree 有自己的 toplevel 與 git-dir, 所以守衛狀態天然分開。同一工作樹內硬要並行做不到,且是刻意設計 —— hooks 分不清寫入來自哪個 session。

守衛掛載(條數與清單以 hooks/hooks.json 為準):PreToolUse = devflow-guard(Edit|Write|Read)、history-guard(Edit|Write,不受武裝狀態影響)、 devflow-prebash(Bash 事前)、devflow-dispatch-guard(Task|Agent,派工分層守衛); PostToolUse = devtalk-guard(盲原則, 不同子系統)、devflow-postbash(Bash 事後偵測)。想確認整套沒壞:跑 ~/.claude/plugins/cache/dev-flow/dev-flow/<version>/hooks/selftest.sh(動態發現所有案例,自建 temp repo 後自清)。

T 級並行(選配):Candidate 到 ACCEPTED

5-tasks.md frontmatter 明寫 execution.mode: parallel 才啟用 (缺省 sequential,行為不變)。每 T 一個 task worktree(task/<slug>/T-n, 同 Wave 同 Base SHA),守衛以 --task 釘單 T scope。核心規則:未過 Review 的 Candidate 不得進正式 integration branch、不得標完成,只有 ACCEPTED 才勾 checkbox (ASCII 正本:README §5「T 級並行」;細節 notes/design/parallel-stage6.md)。

⑤ 常見卡關 FAQ

這章要你懂:五種最常撞到的狀況各有固定修法 —— 沒有一種需要你自由心證,照著走就行。

守衛擋住怎麼辦?

先看是③三張卡的哪一種,照對應處置走。核心原則只有一條:分不清 L1/L2 一律當 L2 —— devflow-exec.sh stop,不要自由心證硬闖。

忘了 stop 怎麼辦?

上個 session 結束時沒跑 stop,旗標留著,有兩種徵狀:

  • devflow-exec.sh status 平時只印 slug/scope/sentinel 狀態;旗標存在超過 24 小時 才會多印一行「旗標已存在 N 天」警告;dev-setup check 也會把「陳年旗標」列為 broken 狀態的異常項
  • 更糟的情況:sentinel 檔案還在但 .devflow/exec.json 被誤刪或損壞 —— 這時 hooks 是 fail-closed,會擋掉所有 Edit/Write/Read,不是靜默放行; status 會印「旗標損壞/異常」訊息

修法:確認沒人在跑該 feature 後,跑 devflow-exec.sh stop 清掉,需要時重新 start。

5-tasks 的 Files 格式怎麼寫(機械可解析)?

## T-1 export
- Covers: R-1 / S-1
- Files: ./src/api/export.ts, src/api/export.test.ts
- Verify: `npm test -- export`
- Blocked-by: —

每個 ## T-n 都必填 Covers、Files、Verify、Blocked-by。Files 逗號分隔多檔; 整個目錄要收作前綴放行,目錄結尾要加 /(如 src/jobs/ 會放行該目錄下所有檔案)。Files 一律以 Git repository root 為相對根: ./src/api/export.ts 會正規化為 src/api/export.ts,不可寫絕對路徑、 .. traversal、空值或含糊的 root。monorepo 中 internal/x_test.go 與 backend-go/internal/x_test.go 是兩個不同 scope;前者不會放行後者。planned new file 可直接列入,不必先存在。

scope 太寬的警告怎麼處理?

只有 Files 值(去掉頭尾斜線後)命中固定字集 {"docs", "src", "app", "lib"} 才會觸發 —— 這是警告,不是硬擋, start 仍會成功,只是等於整個目錄都在 scope 內,guard 形同虛設。 建議回 5-tasks 把 Files 收斂到實際會動的檔案,再重新 start。 ""、"." 與任何正規化後指向 repository root 的條目是硬拒絕, 不是 scope 過寬警告。沒命中固定字集的「寬」(例如某個很大的子目錄)不會被這條規則抓到, 靠 5-tasks 撰寫時自己把關。

既有 external workflow artifacts 會被改動嗎?

不會。dev-setup install 會保留所有未識別的外部 workflow 目錄與產物: 不移動、不覆蓋、不刪除。外部 workflow 是專案層選擇,dev-flow 不轉換、不接管、 也不把它當成官方替代執行系統。

同一張七階段圖,額外標出兩個新手常忽略的地方:虛線框 = 要/建議另開 session 的站(1 討論必開;3 原型、6 實作建議另開; 2/4/5 留在主 session,7 的隔離在 reviewer agent 層 —— 完整表見 README §10「Session 邊界」); 紅色虛線括號 = 執行守衛的武裝區間(start 到 stop 之間)。

紫色 = opus(規劃/派工層);gate reviewer 不指定模型; 青色 = sonnet(執行/產檔層);Stage 6 內部另有 haiku 起步的 T 執行層,見④模型分層速查表。

Stage 6 全部 T ACCEPTED 之後的跨階段收束(sequential/parallel 皆同): 先跑 Final Fresh Gauntlet(綁定當下 source SHA 的 Final Fresh Run + Evidence 契約, README §7 G3 錨定義),全過才進 G3。Gauntlet PASS 不取代雙軸 code review。
