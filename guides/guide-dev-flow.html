③ 七份文件

這章要你懂:七份文件跟著 feature 生死,.claude/rules/ 不跟 —— 前者過完 gate 就封存,後者永生且每 session 自動注入。搞混會出事:把流程規則寫進 rules, 圍欄② 的「盲」會全滅。

七份文件 vs .claude/rules/*.md:兩種生命週期

紅虛線是生命週期分界:上下兩排沒有任何箭頭相連,因為 rules 檔不跟 gate 走。 它的生命週期是「永生」—— 不隨 feature 結案封存,內容是架構不變量 / 技術慣例 / 坑。 下排是 dev-setup install 時產草稿到你核可的路徑:素材來自你指名的 external workflow artifacts 與 CLAUDE.md 的技術規則段,再派 sonnet 掃 codebase 抓候選 —— 留著 【待確認】 的條目不得被當事實引用。 另:4-spec 只寫本次 delta,不重抄 rules(見 _templates/4-spec.md 頂註)。

執行清單四原則(Stage 2/3/4/6/7;清單全文住各模板頂註,Stage 1 同款機制內建於 /dev-talk):①開場第一動把清單建成 todo,每步有「完成 =」客觀條件,達成才勾; ②交審前必過自檢步 —— 產物勾稽、附證據,不憑印象;③禁跳項、禁併項; ④完成條件達不成 → 回上游步驟補,不硬過。

④ 每站執行清單(逐字收錄自 _templates/ 頂註)

這章要你懂:本章不是解釋,是規則正本的複本 —— 綠色左邊條的每一塊都是 逐字抄來的,一個字都沒改寫。要看某一站進場先做什麼,展開該站的區塊照著做就對了。

本節收錄 5 站(Stage 2/3/4/6/7)、共 7 個區塊。這章是 保護區,不是壓縮對象 —— 底下每一塊的內容都與 _templates/ 逐字相同, 只在區塊外圍加了綠色標記讓你分辨「規則」與「解釋」。

每個區塊皆逐字抽自對應模板檔頂端的 blockquote 註解,只做 markdown → HTML 的格式轉換: **粗體** → <strong>、去掉行首 > 引言符號、條列項目換行 → <br> (單條內部的手動折行則接續成一行,避免在較寬版面出現參差斷行)。核對方法:兩側各自收斂空白字元、拿掉 **/<br>/<strong>等格式標記後逐字元比對,結果見任務回報 —— 不是宣稱位元組全同, 是宣稱「拿掉格式標記後,文字內容零差異」。

Stage 2 — 收斂(G1)

把 1 的發散收成一個選定方案;完成後依 README §7 的 reviewer fallback 取得 G1 核准才進 4。

規則正本 · Stage 2 執行清單(逐字抄自 _templates/2-decision.md 頂註)

展開逐字原文

執行清單(開場第一動建成 todo;逐步達成「完成 =」才勾;禁跳項、禁併項): 0. 接手盤點:只讀 1-discussion.md(對話不是契約)+ CONTEXT.md。核 status=approved、 OQ 全三態;缺 → 退回討論。從 Goals/驗收雛形/[>] 移交項提煉「待收斂決策點」, 連同討論期 owner 已自拍的板一併清點。 完成 = 決策點清單經使用者確認(確認紀錄節留一行)。

  1. 方案生成:每決策點 2-3 個 approach 填表,禁單案過場;優劣必有背書 —— 引 1-discussion 事實或本階段查證(留紀錄),禁憑空斷言。完成 = 表齊、每格非空。
  2. 壓測定案:對推薦案逼問失敗模式/邊界/最貴風險 → Risks & Mitigations(每風險 有對策);Success Criteria 逐條可量測(7-review 對照用)。完成 = 兩節齊、 無不可量測句。
  3. 定稿:Decision 一句話+範圍、Rejected 逐案一句棄因、Rationale、Scope & Non-Goals。 完成 = 節全齊、無佔位符。
  4. Owner Calls 清點:owner 沒問使用者、自己拍的板逐條收進 Owner Calls 節 (收錄判準見該節註;上層逐條 OC-n,下層內部項一段帶過)。特別掃兩型必收必標: 裁決延伸(使用者只被問到 X,owner 套到 Y/Z)、裁決收窄(使用者要 A, 實作成 A 減某部分)。完成 = 步 6 第⑥掃的歸屬雙向對應成立。
  5. ADR 晉升檢查:三條件逐條答;全是 → 抄 docs/adr/。完成 = 三答落檔。
  6. 自檢(交審前重讀全檔):①每案優劣有背書?②Decision 覆蓋 1 的每條 Goal (漏的進 Non-Goals)?③[>] 移交項都有著落?④Success Criteria 可量測? ⑤Rejected 無空棄因?⑥歸屬雙向對應:正向 — 步 0 每個決策點皆有使用者 裁決(確認紀錄有痕)或 ≥1 條 OC 承接(一對多合法)?反向 — 每條 OC(上層、 下層皆算)皆可追溯到某決策點,或標「流程層」?延伸/收窄算新增決策點。 任一向斷鏈 = 漏收或無主。問題 → 改檔或回步 1。⑦現況外移:產出有無 成段/成表的「是什麼」內容(描述系統現況或既有結構——schema、資料字典、 介面清單——而非本次決策)?有 → 外移 docs/specs/,本檔只留決策與為什麼。 完成 = 七掃清零(⑥含雙向對應成立)。
  7. G1 送審:html twin(方案架構圖,比較期並排;OC 待裁決置頂)→ in-review → reviewer。審查者依序:適格人類 reviewer → fresh-context reviewer Agent → owner 自審(有記錄的最後手段)。G1 = 方向核准 + Owner Calls 全裁決(有未裁決 OC 不得過;正本 README §7)。核准 → 三連動 (frontmatter/STATUS/twin)。完成 = verdict 記錄+三連動齊。

Stage 3 — 原型(選配)

throwaway 實驗回答 2-decision 遺留的技術/UI 疑問;code 一律進 throwaway branch,禁進 main; 答案回寫 2-decision,無獨立 gate,回寫完成即終態(approved)。

規則正本 · Stage 3 執行清單(逐字抄自 _templates/3-prototype.md 頂註)

展開逐字原文

執行清單(開場第一動建成 todo;逐步達成「完成 =」才勾;禁跳項、禁併項): 0. 定義疑問:引 2-decision 的哪個 Risk/open point;寫清「答案長什麼樣才算回答了」。 完成 = Question 節落檔。

  1. 實驗:code → throwaway branch;純資料實驗 → scratchpad。完成 = Method 節記 branch 名/實驗位置與驗法。
  2. 收證:Result 記答案+證據(輸出摘要/截圖/挑選 events)。完成 = 每個 Question 有證據背書。
  3. 回寫:Verdict 記回寫 2-decision 哪一條 + branch/實驗產物處置(封存/刪), 並在 2-decision「確認紀錄」節留一行(prototype 回寫 | 日期)。 完成 = 2-decision 對應處已實際更新+留痕。
  4. 收尾:結構圖節補齊;frontmatter status 改 approved(Stage 3 無 gate, 回寫完成即終態)、註解同步為最新事實(內文說已回寫,註解不得還寫待回寫)。 完成 = status=approved 且 frontmatter 與內文零矛盾。

Stage 4 — 規格(G2)

本次變更的可測契約(openspec delta 格式)。先過反模糊三律(防偷懶條文),再走執行清單; G2 = R/S 全審 + Drafting Decisions 全裁決 + Verification Profile(依 lane 正確填寫) + Demo verdict(條件式),有未裁決不得過,全文見 README §7。

規則正本 · Stage 4 反模糊三律(逐字抄自 _templates/4-spec.md 頂註)

展開逐字原文

反模糊三律(防偷懶條文):

  1. 每條 S 必須可直接轉成一個測試:含具體輸入與可斷言輸出;禁模糊詞 (適當/正確/合理/必要時/妥善/robust/等等/視情況)。
  2. 未定事項禁寫「TBD/之後再說/實作再定」—— 只能列入 Drafting Decisions (標待裁決)或退回提問。
  3. G2 逐 S 自問:「fresh 工程師只看這條,寫得出測試嗎?」寫不出 = 重寫。

規則正本 · Stage 4 執行清單(逐字抄自 _templates/4-spec.md 頂註)

展開逐字原文

執行清單(開場第一動建成 todo;逐步達成「完成 =」才勾;禁跳項併項、禁一發全生): 0. 接手盤點:先前站核對 —— 2-decision status=approved(G1 過)?3-prototype 若 存在,findings 已回寫 2-decision 且 frontmatter 收尾?缺 → 停,回補。再讀 1-discussion(驗收雛形/OQ)、2-decision(Decision/Scope/Success Criteria)、 living spec 相關域。完成 = 前站核對過 + 雙源清點回報(雛形 N 條、living 受影響條文)。

  1. 雙源列 R:驗收雛形逐條 → ADDED;living spec 受影響 → MODIFIED/REMOVED (引原條文)。完成 = R 清單經使用者確認範圍(確認紀錄節留一行)。
  2. 逐 R 展開 S:一次一個 R,GWT 寫到「可直接變一個測試」(具體輸入+可斷言輸出), 每 S 承接 1-discussion 該條驗收雛形的「觀測方式」(從哪看/看到什麼算對/ 拿什麼資料試;雛形沒寫就在此補齊,純內部行為註明「無外部現象」)。 段段給使用者確認。完成 = 全 R 展開、每 S 有觀測欄、每段有確認(確認紀錄節留一行)。
  3. 邊界收尾:Acceptance Criteria(全 S 綠+回歸+非功能;行為不變 → golden master)、 Out of Scope、Diff Budget、Dependencies;同步填 Verification Profile(含 lane: 欄,Lane 規則見該節;Risk 判準見該節;Risk: high → Failure Model 表必填)與 Design Boundary Contract(條件式:觸發條件見該節,全未命中才可 n-a + 具體理由; Fast lane 不豁免觸發條件)。 Stage 3 對帳:逐一核對 3-prototype Demo Script 場景。每個已 ACCEPTED 的場景 必須對應至少一條 R/S,或在 Out of Scope 明列排除理由;沒有 Stage 3 時記 N/A。 Method 走查條列也算 ACCEPTED 行為的下落來源之一;Operational Context 的 Recovery: 欄位內容也算下落。 完成 = 四節齊 + Verification Profile 填畢 + Design Boundary Contract 有結論 (applicable 全填 / n-a 附理由)+ Stage 3 對帳逐場有下落。
  4. Drafting Decisions 清點:草擬自拍板逐條(決策|理由|棄項|待人審);全文掃 TBD/之後再說/實作再定 → 命中即轉 DD 或退回提問。完成 = 掃描零殘留。
  5. 自檢(反模糊掃描):先跑機械關卡 scripts/check-spec-gate.sh <本檔路徑> (C1 每 S 有觀測欄 / C2 Profile 可解析 / C3 lane×Risk 合法 / C4 模糊詞 / C5 DD 無殘留待裁決);紅了先修再往下,它擋的都是模板明文要求卻沒人擋的項。 機械過了才做人工部分:鏈檢每條驗收雛形 ≥1 個 S 承接、每 MODIFIED 有原文引用。 任一否 → 重寫該 S;(選配)每 S 產 named test skeleton 入 Test Skeletons 節。 完成 = 機械關卡 exit 0 + 逐 S 打勾 + 鏈檢清零。
  6. G2 送審:html twin(R 級行為流程圖;DD 待裁決置頂)→ in-review → reviewer。 審查者依序:適格人類 reviewer → fresh-context reviewer Agent → owner 自審 (有記錄的最後手段)。G2 審查關鍵條件 = R/S 全審 + DD 全裁決
    • Verification Profile(依 lane 正確填寫;未填視為步 3 未完成)

⑤ Gate 規則卡

這章要你懂:三道 gate 問的是三個不同的問題 —— G1 問方向、G2 問契約寫得對不對、G3 問做出來的對不對。共同的硬規則只有一條: 核准者不能是該文檔的 owner。

G1 —— 方向對不對

2-decision:方向核准 + Owner Calls 全裁決,有未裁決 OC 不得過。

G2 —— 契約寫得對不對

4-spec:R/S 全審 + Drafting Decisions 全裁決 + Verification Profile(依 lane 正確填寫)+ Demo verdict(條件式),有未裁決項不得過(條件全文見 README §7)。

G3 —— 做出來的對不對

7-review:本次 S 全綠 + 既有測試套件全綠 + 現象證據逐 S 相符 + Evidence 契約全過(八點定義見 README §7);本模板另要求無 🔴 才 PASS。

author ≠ approver

G1/G2/G3 的核准者不可以是該文檔的 owner。無適格人類第二人不跳過 Agent fallback;只有前兩種 reviewer 都不可用時才記錄 owner 自審,不假裝有四眼。

Quiz gate

不可逆改動(schema/API 契約/跨模組介面)merge 前必做:AI 出 3-5 題考 approver,全對才 merge;其餘 full lane 選配(approver 可要求),fast lane 免。

三連動

每過一個 gate:frontmatter status + STATUS.md + 同名 html twin 三者同步更新,禁漏一項。

規劃層 git

接手起手先看 git status,與本 feature 無關的改動 → 回報使用者處置,不與文檔混流;每過一個 gate,把該階段文檔commit 一次(只含文檔)。Stage 1-5 規劃階段文檔可直接落 develop(純文檔無程式碼,低風險);Stage 6 起手式才開 feature branch。

規則正本 · 審查者產生順序(逐字抄自 README §7)

  • 審查者產生:G1/G2/G3 一律依序選 適格人類 reviewer → fresh-context reviewer Agent → owner 自審(有記錄的最後手段)。Agent 必須是乾淨 context,只給審核對象+基準+回報格式,不給 作者結論;verdict 與審者身分記 reviewers 欄(如 [independent-fresh-context-reviewer])
    • 檔內留 round 紀錄。owner 自審僅能作為有記錄的最後手段,不假裝有四眼。

frontmatter 狀態機

只有 Stage 7 會走到 shipped;上游 artifact 停在 approved, 作為各自 gate 的核准紀錄。superseded 是被後續決策取代,不是失敗。

⑥ 執行守衛:dev-flow 掛在 agent 生命週期的哪裡

這章要你懂:dev-flow 沒有自己的一套事件系統 —— 它整套掛在 Claude Code agent 既有的生命週期事件上(hook 註冊 + skill 的 progressive disclosure)。「掛上去」與 「沒掛上」對執行者長得一模一樣,所以知道哪一格會醒、哪一格從來不管事, 比背誦 hook 名字重要。

藍框(accent 色邊)的節點是 dev-flow 掛東西的格子;灰框的是 harness 自己的內部步驟, dev-flow 不掛鉤。右側小迴圈是「回 PreToolUse 重複下一次工具呼叫」;左側大迴圈是 resume 接續舊 session —— 兩個迴圈不是同一件事,細節見下方 3 與 6。

來源:~/dev/dev-flow/dev-setup-record.html 對應段落與 ~/.claude/plugins/cache/dev-flow/dev-flow/<version>/hooks/ 原始碼; 生命週期骨架本身是 Claude Code harness 既有事件,dev-flow 只是掛客,不重新定義它們。

1. Session Start:什麼進了 context

每次開新 session(或 resume 接續舊 session)都重新走一次這張表 —— 「常駐」與 「觸發才載」是兩種完全不同的成本,搞混會誤判「這份文件 AI 一定看得到」。

項目什麼時候進 context、進多少
user / 專案 CLAUDE.md(含 @import)全量常駐
子目錄 CLAUDE.md讀到該目錄底下的檔案時才載,不是開場常駐
rules/*.md無 paths: 欄 → 開場即載;有 paths: → 路徑命中才載
output-style開場就進 system prompt
skills只載名稱 + 描述(一行);本文(SKILL.md 全文)要本輪對話觸發到才載 —— 見下方 2
agents只載描述,不載本體
MEMORY.md前 200 行或 25KB,先到者為界
plugin hooks只是註冊(告訴 harness「這個事件發生時跑這支腳本」), 不會把腳本內容塞進 context;事件真的觸發才執行,執行結果(stdout/exit code)才可能進 context

這張表解釋了一個常見誤解:「hook 已經裝了」不等於「AI 讀過 hook 在防什麼」 —— agent 通常只看得到 hook 擋下時吐回來的錯誤訊息,看不到 hook 原始碼,除非有人明講或它主動去讀檔。

2. UserPromptSubmit

使用者打下 /dev-flow、/dev-setup 這類斜線指令的那一刻,對應 skill 的 SKILL.md 全文才真正進 context —— 這就是 progressive disclosure:開場只認得到「有這個 skill、一句話描述」, 要本文觸發到才把完整內容(路由邏輯、階段動作表、鐵則)換進來。

定位到 Stage 6 時,/dev-flow 路由器會再用 Skill tool 自動載入 dev-run 的 SKILL.md(見下方 5)—— 這是第二層 progressive disclosure,同一機制疊了一次:上一個 skill 的路由邏輯決定要不要展開下一個 skill 的本文, 不是全部 skill 一開場就攤開。

/dev-talk 的讀取白名單(圍欄①)也是靠這一格生效:白名單規則就寫在 /dev-talk 自己的 SKILL.md 裡,展開那一刻才成為當輪 context 的一部分 —— 它是 prompt 約束,不是 hook 機械擋(機械側見下方 4 的 devtalk-guard.sh)。

3. PreToolUse:三支擋在寫入前

這節要你懂:守衛只在 devflow-exec.sh start 到 stop 之間是醒著的,其餘時間靜默沉睡 —— 而「守衛在擋」與「守衛不在」對 執行者長得一模一樣,所以 Stage 6 步 0 的武裝自檢是硬關卡,不是儀式。

hook時機做什麼

5. SubagentStart/Stop:dev-run 派工

Stage 6 由 dev-run 引擎逐 T 派工:worker(haiku 起步,錯一次升 sonnet)與 reviewer(fresh sonnet)各自是獨立 context —— 主線讀過的專案 CLAUDE.md、 這份導覽頁、甚至前一個 T 的討論,都不會自動跟過去。

這正是 Task Context Packet(派 worker 的 prompt;缺一不派)存在的 runtime 理由: 要靠 prompt 把 run_id、slug、T-id、Intent、Covers 的 R/S 原文、 Test Skeleton、Boundaries、living spec 節錄等塞進去,worker 才「知道自己在做什麼、 不能碰什麼」。反過來說 —— 5-tasks.md 模板為什麼 Intent/Boundaries 是六個必填欄之二:它們不是寫給人看的裝飾,是 Task Context Packet 唯一的取材來源;缺欄 = 派工 prompt 少一塊,worker 只能自己猜。

派工 prompt 另有硬性禁令(圍欄④,見下節表):不得塞完整討論逐字稿,只帶 4-spec Operational Context 的最小子集 —— 獨立 context 解決「知道太少」,圍欄④解決「知道太多」,兩者互補 不互相取代。

6. Stop 與壓縮:為什麼文件是正本

Stop 之後(以及更關鍵的 PreCompact/PostCompact)—— 上下文超過門檻會被壓縮,壓縮做的事情是裁剪:已展開的 skill 本文會被裁掉, 被裁後不會自動重新展開,而 skill 描述清單(見上方 1)也不會因為壓縮而重新整批注入。 換句話說,session 記憶是會退化的 —— 這一輪還記得的細節,壓縮之後可能就不在了, 而且退化前後對使用者長得一樣正常。

這正是 6-implementation-notes.md「即時記帳」這條紀律的 runtime 理由:Progress Log、 Decisions、Self-Review 要在動作發生的當下就寫進 md,不能靠「等一下再一起補」——因為「等一下」可能 跨過一次壓縮,腦內記憶會消失但檔案不會。md 是唯一正本,對話不是契約,原因不是 流程潔癖,是壓縮這一格真的會把沒落檔的東西吃掉。

⑧ 大案與切片

這章要你懂:「案子很大」不等於「可以切」 —— 大小只是要你回頭評估的訊號, 真正的門檻是有沒有合法接縫。沒有接縫就不切,硬切出來的片會互相咬住。

上排兩份全片共用、只做一次;下排每片各走一條完整的 4→7,各有自己的 G2/G3。 片 A 到片 B 的那條線不是「執行順序」而是契約凍結順序 —— 後片只能依賴前片對外產出。

大案先評估切片可行性:≥3 個可獨立 phase、Diff Budget >15 檔、跨 repo, 都是「可能需要切片」的訊號,不是強制切片條件,也不證明已有合法接縫。

合法接縫

只能在「後片單純依賴前片對外產出(介面/資料契約), 不依賴其內部設計」的架構邊界切;不得只按數量平分,repo 分開也不自動是接縫。

軟訊號

單份 4-spec >~40 條 scenario,或 reviewer 預判一次審不動, 也要回頭評估切片;仍不能跳過合法接縫判準。

無接縫時

若拆分會讓後片依賴前片內部設計,保留單一 4 → 5 → 6 → 7 管線。

有合法接縫時,1-discussion/2-decision 全片共用;每片各走 4-spec → 5-tasks → 6-notes → 7-review,各有 G2/G3。每片 frontmatter 明載 parent,R/S ID 跨片不重號,並依片序凍結前片對外契約;前片契約改動時, 後片必須 impact review。

長時間與跨 session 依 STATUS.md、5-tasks.md、 6-implementation-notes.md 接力;無人看管的多 phase orchestration 屬專案層選擇, dev-flow 不依賴也不規範它。完整規則見 README §13–14。
