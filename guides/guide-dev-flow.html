③ 七份文件

這章要你懂:七份文件跟著 feature 生死,.claude/rules/ 不跟 —— 前者過完 gate 就封存,後者永生且每 session 自動注入。搞混會出事:把流程規則寫進 rules, 圍欄② 的「盲」會全滅。

人要翻長期決策或改版歷史,不要讀生 md: 決策列表 · 改版歷史。 md 仍是 git 正本。這兩頁不是 Agent Memory。

白話對照+範例(非正本;正本=上方模板逐字)

這一站你在做的事,一句話 = 把上一站發散出來的各種可能做法,收成一個定案,並讓有裁決權的人核准放行。

  • 0. 接手盤點:先讀上一站定稿的內容,不是討論當下隨口講的話——確認它已經核准、裡面的待答問題都有了答案;沒有的話整組退回去,不能往下做。再把驗收草案、還沒交接完的項目裡藏著的「等一下要決定的事」通通挑出來,連同自己已經先斬後奏拍板的部分一起算,列成一張清單,並且要有使用者確認過的紀錄可查。
  • 1. 方案生成:針對清單上每一個要決定的點,生出 2 到 3 個不同做法,不能只端出一個方案叫人選;每個方案的優缺點都要有根據撐腰——引前一站寫下的事實,或這次自己查證過的東西,不能憑感覺講。
  • 2. 壓測定案:挑出打算推薦的那個方案後,故意去找它的破綻——什麼情況下會失敗、界線在哪裡、最貴的風險是什麼,寫進風險清單;把「怎樣才算做成了」的每一條寫到能拿尺量的程度,不能只寫「大概好用」這種空話。
  • 3. 定稿:把決定寫成一句話講清楚範圍、沒選的方案各自寫一句為什麼被刷掉、選這個方案的理由、這次做的範圍跟不做的範圍,四塊都要寫滿,不能留空格佔位。開工後 owner 改了使用者看得到的行為:G3 還沒過就先改這份 Decision 再重走 4→5→6→7;G3 過了就另開薄刀,不准改已封包;只改文字、行為不變走原包 HISTORY。已經核准的 Decision 被推翻,不是合法的待裁決項。
  • 4. Owner Calls 清點:把這次自己做主、沒有回頭問使用者的判斷,一條一條記下來;特別要抓兩種——使用者只講了小範圍,卻被套用到更大範圍;或使用者要的是完整的東西,卻只做了一部分。
  • 5. ADR 晉升檢查:三個問題各自答一次——這個決定回頭改很難嗎?這個決定違反直覺嗎?這裡面有真正的取捨嗎?三個都答「是」才需要把這份決定另外抄一份到架構決策記錄裡,否則留在這份文件就好。
  • 6. 自檢:送審前重讀整份文件,自己問自己七個問題,包括:每個方案的優缺點有沒有根據?決定有沒有涵蓋上一站的每個目標?還沒交接完的項目都有著落了嗎?每一條「怎樣算做成」都能拿尺量嗎?被刷掉的方案有沒有隨便寫個理由打發?自己做主的判斷跟使用者的裁決兩邊對不對得起來?文件裡有沒有大段在講「系統現在長什麼樣」而不是這次要決定什麼,有的話要搬去別處。七個問題都答完才算過關。
  • 7. G1 送審:把方案架構圖做成可審查的網頁版本,標成審查中狀態,交給審查者——優先找夠格的真人,真人不行才找一個沒看過這次討論、乾淨腦袋的 AI,最後手段才是自己審自己。要真的過關,兩件事都要成立:審查者同意方向是對的,而且自己做主的每一條判斷都已經被人裁決(還沒裁決的不能過)。過了之後同步更新文件狀態欄、進度追蹤表、審查用網頁版三個地方。

執行清單(開場第一動建成 todo;逐步達成「完成 =」才勾;禁跳項併項、禁一發全生): 0. 前置:4-spec 須 status=approved(G2 過);讀 4-spec 全部 R/S 建立盤點基礎, 建 todo 一 T 一項。完成 = approved 已核對 + R/S 全集清點回報。

  1. 切 T:順序 = tracer bullet(先打通最薄端到端縱切,再逐層加厚);判準見上方 「一個 T 一個關注點」與「T 自足律」—— 每個 T 必須答得出「完成後系統/使用者多了什麼可觀測行為」,答不出即水平切層 徵兆,應與相鄰 T 合併或重界定,不得整份按 DB→Repo→Service→API→UI 逐層分 (機械提示見 scripts/check-task-slicing.sh,warning-only、永不 exit 1, 不能取代 reviewer 判斷);每個 T 必須有一個能 RED→GREEN 的測試,純 migration／infra 型 T 一樣要測,只是測形狀(見上「T 自足律」)。 完成 = 每個 T 皆答得出可觀測行為、無按架構層整份切分。
  2. 填欄:Covers 標 R/S id 且全 S 皆被至少一個 T 承接(追溯鏈頂端);Files 以 Git repository root 相對路徑列出,含對應測試檔(D-39 四象限判準見上「Files 該含 哪些測試檔」節);Verify 單行純指令,-run/-k/--filter 篩選器須帶案例數 斷言(強制形狀見上方「篩選子集必須自帶案例數斷言」那條的骨架),開工前先原樣跑一次, 依「①已經綠→補計數或改條件 ②不可能綠→停,修欄位,記 L1③綠不了但方向對→正常開工」三種結果處置;Intent 一句寫可觀測行為,Boundaries 寫硬約束/禁區,Design Boundary Contract 為 applicable 時比照「Design Boundary 摘錄規則」摘錄該 T 最小子集;續行不得 以保留欄名開頭(見上方「續行禁令」)。 完成 = 四必填欄齊備、Verify 已原樣跑過一次並記錄結果、Intent/Boundaries 各 一句到位。
  3. 依賴:填 Blocked-by(硬執行依賴,拓撲序不成環);parallel 模式選配填 Integrate-after(軟整合依賴)/Risk/Review-mode/Semantic-conflicts-with, 不必手排 wave——Wave 由引擎從 Blocked-by + Files overlap 自動派生(見上「並行 選配欄位」)。完成 = 每個 T 的 Blocked-by 已核對、拓撲序無誤。
  4. 自檢:逐 T 核對四必填欄(Covers/Files/Verify/Blocked-by)齊全、續行未踩保留 欄名——缺一欄或踩中,contract_ref.py 的 parse_5_tasks 即判為 parse error,start fail-closed 拒啟(見上「續行禁令」)。完成 = 逐 T 核對零缺欄、 零保留欄遮蔽。

  6. 定稿:frontmatter status 由 draft 轉 approved(5-tasks 不是 gate 站,無 G 編號、免 reviewer 核准,owner 自行定案即可)。完成 = status 已更新 + twin 與 md 一致。
白話對照+範例(非正本;正本=上方模板逐字)

這一站你在做的事,一句話 = 把上一站定案的規格,拆成一張一張可以勾選、有明確驗證方法的工作單,讓人或 AI 拿到其中一張就能直接動工。

  • 0. 前置:動工前先確認上一站的規格文件已經核准過,並把規格裡的每一條需求與行為描述通讀一遍,當作拆工作單的依據。
  • 1. 切工作單:順序照「先打通一條最細的端到端路徑,再逐層加厚」走,不要整批照資料庫→存取層→服務層→介面→畫面這種技術分層去切。每張工作單都要能回答「做完之後,使用者或系統多了什麼看得到的行為」,答不出來就代表切錯了,要跟旁邊的工作單合併或重新界定。就算是純粹建資料表、加欄位這種沒有明顯業務邏輯的工作單,也要有一個「做完了會變綠」的測試,只是測的是形狀對不對(表存不存在、型別對不對)。有一個小工具會提醒「疑似整批照技術分層切」的情況,但它只是提醒不會擋人,也不能取代人工判斷。
  • 2. 填欄位:每張工作單要標清楚承接了規格裡哪一條需求與行為描述(規格裡每一條都至少要被一張工作單接住,不能漏);要動的檔案要列清楚(相對路徑,連測試檔案都要列進去);驗證方法要寫成一行可以直接貼進終端機執行的指令,若用篩選條件只挑幾個測試跑,一定要順便斷言「真的跑了幾個」,不然篩選條件沒對到任何測試、指令照樣回報成功,會誤以為測試都通過了。這個驗證指令動工前要先照原樣跑一次看結果——已經是綠燈代表這條驗證沒有鑑別力,需要加強;照理說不可能綠卻已經綠了,代表哪裡有問題要停下來查;還沒綠但方向正確,才是正常狀態可以開工。另外每張工作單要一句話寫「做完後多了什麼看得到的行為」,以及有沒有不能踩的硬性限制或禁區。
  • 3. 填依賴關係:寫清楚每張工作單要等哪一張先做完(這是真正的硬性順序,不能提前做);允許同時進行的模式下還有一些選填欄位,但不需要自己手動排「誰跟誰可以同時做」,系統會自己從依賴關係與檔案有沒有重疊算出來。
  • 4. 自我檢查:逐張工作單核對四個必填欄位(承接的需求、要動的檔案、驗證方法、依賴關係)有沒有填齊,格式有沒有踩到會被系統誤判成別的欄位的陷阱——少填一項或踩到陷阱,系統在真正要開工時會直接拒絕啟動,不會讓你帶著漏洞硬做下去。
  • 5. 看一眼執行看板:用固定的工具把這份工作單文件轉成一份看板網頁,看板會自動標出整體進度概況、每張工作單卡片(缺欄位的卡片會用顏色標出來)、限制條件收合起來不佔畫面、還有依照依賴關係自動畫出的執行順序圖。四件事都要在,少一件就代表這一步沒做完。
  • 6. 定稿:把文件狀態從「草稿」改成「已核准」——這一站沒有審查關卡,不需要另外找人核准,自己確認好就可以往下一站走。

執行清單(開場第一動建成 todo;逐步達成「完成 =」才勾;禁跳項、禁併 T): 0. 起手式,分三小步(0a 開 branch 與錨點/0b worktree 隔離確認/0c 守衛與 doctor 自檢),各自查驗完成才算這步完成: 0a. 開 branch 與錨點:圍欄自查 —— 只讀 4-spec/5-tasks/6-notes/長期記憶查詢結果/ living spec,禁讀 1/2/3(要翻才寫得出 = spec 不完整 → 停,回 G2)。開 feature branch —— 開 branch 與記分岔錨點是同一個動作的兩半,中間不准插別的事, 照下面四步做,不可拆。錨點 FORK_INTEGRATION_SHA = 開這條 branch 的當下整合 分支(develop 或 main,依專案)的最新點;Stage 7 的整合回歸工具靠它才算 得出「分岔之後對方多了什麼」—— 事後回頭查會查到已經前進過的點,錨點當場 失效:

git fetch <remote>
    FORK=$(git rev-parse --verify "refs/remotes/<remote>/<整合分支>^{commit}")
    git switch -c <feature-branch> "$FORK"
    test "$(git rev-parse HEAD)" = "$FORK"   # 不相等 = 中間出過事,停下重來

並行(多 feature)改用 worktree 時是另一組四步,不是把上面那組改一個字:

git fetch <remote>
    FORK=$(git rev-parse --verify "refs/remotes/<remote>/<整合分支>^{commit}")
    git worktree add <worktree-path> -b <feature-branch> "$FORK"
    test "$(git -C <worktree-path> rev-parse HEAD)" = "$FORK"

⚠️ 第四步一定要帶 -C <worktree-path> —— 少了它,git rev-parse HEAD 讀的是 你現在站的那個 checkout,不是剛建好的 worktree:驗證會通過,但它驗的是別人, 新 worktree 建在錯的點上也照樣放行。git worktree add 也要明示 "$FORK", 不要讓它預設從當前 HEAD 建。四步跑完,立刻把 $FORK 那 40 碼用下面這個 逐字欄位寫進本檔(Stage 7 整合回歸工具 --fork-sha 吃的就是這個欄位的值):

FORK_INTEGRATION_SHA: <40 碼>

之後不管 merge/rebase 幾次都不准更新它 —— 它記的是「歷史上的那個時刻」, 不是「現在的狀態」,一更新就退化成 merge-base,等於沒有。 完成 = 讀取清單回報 + branch 就位(或 worktree 建好且 HEAD 驗證通過)+ FORK_INTEGRATION_SHA 已記進本檔(40 碼全長)。 0b. worktree 隔離確認:多 feature 並行(多 worktree)另做兩件事: ①STATUS.md 不在 worktree 內改 —— 它只在整合分支(develop 或 main,依專案) 上維護,規則與理由見 STATUS 模板頂註;②確認執行環境已隔離:容器名/對外 port (兩個 worktree 同時起得來嗎?)、資料庫(共用同一個 DB 時,migration 版本 紀錄表會混進兩個 feature 的版本,導致其中一邊 apply 被拒)、快取/訊息佇列/ 檔案上傳目錄等有狀態的外部依賴。隔離方式依專案技術棧自理,母版不規定做法 —— 母版規定了「並行用 worktree」,就要負責講清楚這個規定的代價,所以檢查項要管; 但怎麼隔離是各專案技術棧的事,母版規定做法會變成「規定了但不適用」。 背景案例(佐證,不是本次要照做的事):實例 atlas_schema_revisions, order-intake T-2 實踩。 ⚠️ worktree 交接(並行動線的最後一步):上面兩件事(STATUS 在整合分支上改、 執行環境隔離確認)做完後,明確切進新樹:

cd <worktree-path>          # 從這裡開始,後續所有指令都在這棵樹上跑

後面的 devflow-exec.sh status 必須在這個目錄下跑,它會核對 slug 與 cwd 相符 —— 在原 checkout 跑會核對到別的東西。 worktree 合併(預期,不是 bug):feat worktree 產的 docs/dev html/md 會跟著 branch 走。要併回專案真正在用的整合線(常是 develop 與 testing), 不要把雙生頁只留在 worktree。HISTORY 出廠種子列也會跟著走,可能衝突; 清種子用 history-append.sh --action factory-seed-cleanup(不要每次 upgrade 自動跑),不要手改。 完成 = 執行環境隔離結果已貼進本檔:逐項寫容器名/對外 port/資料庫/快取或佇列/ 檔案上傳目錄各自怎麼隔離的(實際值,不是「已隔離」三個字);單一 worktree、 沒有並行 → 寫 n-a:本 feature 未並行,理由要寫出來。 0c. 守衛與 doctor 自檢:⚠️ 守衛武裝自檢(硬關卡,第一動):跑 devflow-exec.sh status,確認 .devflow/exec.json 存在且 slug 正確。 沒武裝就不准開工 —— guard hook 在 .devflow/exec.json 不存在時是 靜默沉睡的(devflow-lib.py::load_state → return None, "", ""), 於是「守衛在擋」與「守衛不在」對執行者長得一模一樣: 圍欄②(禁讀上游)、契約防篡改、scope 守衛三道全部不會觸發, 而每一份產出看起來都一樣完整。 武裝不了 → 停下回報,不要用「我會自己守 scope」代替。 ⚠️ 同一動作再跑 devflow-doctor.sh(或 devflow-exec.sh doctor):版本握手 fail-closed,回報 INCOMPATIBLE 即停下回報,不得略過繼續。 背景案例(佐證這兩條為何是硬關卡,不是本次要照做的事):2026-08 order-intake 實測 —— ①devflow-exec.sh 因母版 bug 啟動不了(D-9),26 個 T 全程守衛沉睡, Files scope 是人工比對出來的,當下沒人發現,因為沒有任何訊號; ②dev-setup 沒散發齊 devflow-contract.json 與 docs/dev/tools/,doctor 實跑 直接 ⛔ INCOMPATIBLE(fail-closed),但整條 Stage 6→7 沒有任何一步要求跑它, 所以沒有人被擋。 完成 = devflow-exec.sh status 與 devflow-doctor.sh 兩份輸出都貼進本檔。

Final Fresh Run:確認驗證證據那節,是照規格文件指定的入口指令,在當下這個版本重新完整跑一次產生出來的(不是抄舊的),Source SHA 對應到目前這個 commit(git rev-parse HEAD);然後跑一個叫做證據關卡的檢查指令(docs/dev/tools/devflow-evidence-gauntlet.sh)。Gauntlet 自己讀規格文件的必跑層級,漏帶開關不再假裝通過。開工前先確認這個檢查指令真的存在、可以執行;如果不存在,代表專案的安裝步驟沒有跑完整,正確做法是回去把安裝步驟補跑一遍,而不是自己手動複製一支腳本了事。如果實在補不了,就把規格要求的每個驗證層級改成自己逐層手動實跑,並在文件裡清楚寫明「這是降級處理」,不能悄悄假裝跑過了。
  • 2e. Operational Walkthrough:拿規格文件裡每條行為描述寫的「實際工作情境」當劇本,自己走一遍「人真正要做的事」,逐一檢查六種常見的坑——表面上系統功能是通的但人根本沒辦法完成工作;看得到資訊但沒有決定權;系統把「還在等」誤標成「已經完成」;系統外面發生的動作沒辦法追蹤;使用者操作到一半中斷後回不去;資訊過期、缺漏,或多人同時在動同一筆資料。把結果填進走查表(純系統內部、沒有實際工作情境可言的行為就標不適用)。
  • 3. 雙軸審:從兩個角度審這次的改動——一個角度看整體工程品質(發現問題按嚴重度標紅黃綠燈,寫清楚位置、問題、建議),另一個角度逐條核對是不是真的做到規格要求(每條需求都判定符合或偏離)。如果上一站規格有標記「系統邊界契約需要審查」,不另開新的關卡或第三個角度,而是併進這兩個角度裡一起查:工程品質那邊多查有沒有引入不該有的模組依賴、內部細節有沒有外洩、資料歸屬有沒有變、對外介面穩不穩定;規格那邊逐條核對實際改動符不符合這份邊界約定,並過一份「看起來守住邊界、其實被繞過」的檢查清單(Design Integrity Check),抓到的問題併進上面兩邊的發現裡。每個發現都要標明影響了哪些行為描述或任務。如果是 AI 在審查,兩個角度要各自派一個獨立、沒看過對方在查什麼的乾淨腦袋 agent 同時進行(真人審查者可以一人身兼兩個角度);彙整的人只能把兩邊發現的問題並排列出來,不能合併重排、也不能為了讓其中一邊好看而降低問題的嚴重度。每個問題都要引用規格原文或程式碼改動的具體出處撐腰,不能憑空下結論。
  • 4. 對照作者:到這一步才可以去讀實作筆記裡的「自我審查」章節——把自己一路查出來的矩陣,拿去跟原作者寫的自我審查逐條比對差異並裁定;同時檢查原作者記的偏離是不是誠實記錄、他自己選的判斷有沒有其實嚴重到該算是需要回頭重審。如果第 0 步有先把「不准讀實作筆記」這道機械限制打開,現在要先跑解鎖指令(devflow-exec.sh review-unlock <slug>)才讀得到內容(解鎖不代表可以改動別的檔案,寫入範圍仍然限縮住)。
  • 5. Verdict:這次新增的行為測試全綠、既有測試也全綠、每條行為的現象證據都跟預期相符、上面的證據關卡全部通過、而且工程品質那邊沒有任何紅燈,才算過關;只要有紅燈,就判定打回修改,列出每個紅燈項目交回實作者處理——同意的話改掉並寫一句為什麼現在對了,不同意的話要擺出論證,不能做表面功夫應付。改完後回到步驟 1 只驗證改動的部分,不用整個重來。這個打回—修改—重驗的迴圈最多只能繞三輪,第三輪還是打回修改的話,就要對每一個問題強制做出裁決(立刻修、記進待辦清單暫緩、或整個案子先停下來),裁決結果要寫進文件裡,不准悄悄不了了之、也不准不記錄就繼續繞下一輪。
  • 6. Exit:把出貨前的檢查清單逐項打勾,全部打勾了才算真正可以出貨;這時候只有這份驗證文件自己的狀態欄位會改成已出貨,前面幾站(討論、決定、原型、規格)的文件狀態仍然保留在已核准,那是它們各自那一關通過的紀錄,不會被這裡蓋過去。

⑤ Gate 規則卡

這章要你懂:三道 gate 問的是三個不同的問題 —— G1 問方向、G2 問契約寫得對不對、G3 問做出來的對不對。共同的硬規則只有一條: 核准者不能是該文檔的 owner。

G1 —— 方向對不對

2-decision:方向核准 + Owner Calls 全裁決,有未裁決 OC 不得過。

G2 —— 契約寫得對不對

4-spec:R/S 全審 + Drafting Decisions 全裁決 + Verification Profile(依 lane 正確填寫)+ Demo verdict(條件式),有未裁決項不得過(條件全文見 README §7)。

G3 —— 做出來的對不對

7-review:本次 S 全綠 + 既有測試套件全綠 + 現象證據逐 S 相符 + Evidence 契約全過(八點定義見 README §7);本模板另要求無 🔴 才 PASS。

author ≠ approver

G1/G2/G3 的核准者不可以是該文檔的 owner。無適格人類第二人不跳過 Agent fallback;只有前兩種 reviewer 都不可用時才記錄 owner 自審,不假裝有四眼。

Quiz gate

不可逆改動(schema/API 契約/跨模組介面)merge 前必做:AI 出 3-5 題考 approver,全對才 merge;其餘 full lane 選配(approver 可要求),fast lane 免。

三連動

每過一個 gate:frontmatter status + STATUS.md + 同名 html twin 三者同步更新,禁漏一項。

規劃層 git

接手起手先看 git status,與本 feature 無關的改動 → 回報使用者處置,不與文檔混流;每過一個 gate,把該階段文檔commit 一次(只含文檔)。Stage 1-5 規劃階段文檔落在整合分支(develop)上(純文檔無程式碼,低風險);該分支有護欄擋直接 commit 時,走短命 branch → commit → 立刻 merge --no-ff 回去,不要把文檔混進 feature branch。Stage 6 起手式才開 feature branch。

規則正本 · 審查者產生順序(逐字抄自 README §7)

  • 審查者產生:G1/G2/G3 一律依序選 適格人類 reviewer → fresh-context reviewer Agent → owner 自審(有記錄的最後手段)。Agent 必須是乾淨 context,只給審核對象+基準+回報格式,不給 作者結論;verdict 與審者身分記 reviewers 欄(如 [independent-fresh-context-reviewer])
    • 檔內留 round 紀錄。owner 自審僅能作為有記錄的最後手段,不假裝有四眼。

frontmatter 狀態機

只有 Stage 7 會走到 shipped;上游 artifact 停在 approved, 作為各自 gate 的核准紀錄。superseded 是被後續決策取代,不是失敗。

⑥ 執行守衛:dev-flow 掛在 agent 生命週期的哪裡

這章要你懂:dev-flow 沒有自己的一套事件系統 —— 它整套掛在 Claude Code agent 既有的生命週期事件上(hook 註冊 + skill 的 progressive disclosure)。「掛上去」與 「沒掛上」對執行者長得一模一樣,所以知道哪一格會醒、哪一格從來不管事, 比背誦 hook 名字重要。

三條走廊由左至右:左 = 灰虛線掛靠事件(harness 會觸發、但 dev-flow 沒掛鉤的旁支);中 = 主幹 ——綠 = session 起點、黃 = dev-flow 可掛鉤的 hook 格、藍 = 工具實際執行、 紅 = Stop、灰 = harness 內部無 hook 語意的段落;右 = dev-flow 實際掛鉤處(留白 = 沒掛,見下方 1-6)。 藍色虛線框「EACH TURN」是使用者一次輸入到 Stop 的一整輪,內含橘色虛線框「AGENTIC LOOP」——每次工具呼叫都繞這一圈, 橘色回邊繞回 PreToolUse;藍色回邊繞回 UserPromptSubmit 開下一輪。右側黑虛線長回邊 「resumed sessions」是 SessionEnd 之後 resume 接續舊 session,回到 SessionStart—— 這與前兩個迴圈不是同一件事。底部六格是不掛在任何一輪節點上的獨立系統事件。每格掛了哪些檔的完整清單 → 附錄:檔案地圖。

來源:~/dev/dev-flow/dev-setup-record.html 對應段落與 ~/.claude/plugins/cache/dev-flow/dev-flow/<version>/hooks/ 原始碼; 生命週期骨架本身是 Claude Code harness 既有事件,dev-flow 只是掛客,不重新定義它們。

1. Session Start:什麼進了 context

每次開新 session(或 resume 接續舊 session)都重新走一次這張表 —— 「常駐」與 「觸發才載」是兩種完全不同的成本,搞混會誤判「這份文件 AI 一定看得到」。

項目什麼時候進 context、進多少
user / 專案 CLAUDE.md(含 @import)全量常駐
子目錄 CLAUDE.md讀到該目錄底下的檔案時才載,不是開場常駐
rules/*.md無 paths: 欄 → 開場即載;有 paths: → 路徑命中才載
output-style開場就進 system prompt
skills只載名稱 + 描述(一行);本文(SKILL.md 全文)要本輪對話觸發到才載 —— 見下方 2
agents只載描述,不載本體
MEMORY.md前 200 行或 25KB,先到者為界
plugin hooks只是註冊(告訴 harness「這個事件發生時跑這支腳本」), 不會把腳本內容塞進 context;事件真的觸發才執行,執行結果(stdout/exit code)才可能進 context

這張表解釋了一個常見誤解:「hook 已經裝了」不等於「AI 讀過 hook 在防什麼」 —— agent 通常只看得到 hook 擋下時吐回來的錯誤訊息,看不到 hook 原始碼,除非有人明講或它主動去讀檔。

2. UserPromptSubmit

使用者打下 /dev-flow、/dev-setup 這類斜線指令的那一刻,對應 skill 的 SKILL.md 全文才真正進 context —— 這就是 progressive disclosure:開場只認得到「有這個 skill、一句話描述」, 要本文觸發到才把完整內容(路由邏輯、階段動作表、鐵則)換進來。

定位到 Stage 6 時,/dev-flow 路由器會再用 Skill tool 自動載入 dev-run 的 SKILL.md(見下方 5)—— 這是第二層 progressive disclosure,同一機制疊了一次:上一個 skill 的路由邏輯決定要不要展開下一個 skill 的本文, 不是全部 skill 一開場就攤開。

/dev-talk 的讀取白名單(圍欄①)也是靠這一格生效:白名單規則就寫在 /dev-talk 自己的 SKILL.md 裡,展開那一刻才成為當輪 context 的一部分 —— 它是 prompt 約束,不是 hook 機械擋(機械側見下方 4 的 devtalk-guard.sh)。

5. SubagentStart/Stop:dev-run 派工

Stage 6 由 dev-run 引擎逐 T 派工:worker(haiku 起步,錯一次升 sonnet)與 reviewer(fresh sonnet)各自是獨立 context —— 主線讀過的專案 CLAUDE.md、 這份導覽頁、甚至前一個 T 的討論,都不會自動跟過去。

這正是 Task Context Packet(派 worker 的 prompt;缺一不派)存在的 runtime 理由: 要靠 prompt 把 run_id、slug、T-id、Intent、Covers 的 R/S 原文、 Test Skeleton、Boundaries、living spec 節錄等塞進去,worker 才「知道自己在做什麼、 不能碰什麼」。反過來說 —— 5-tasks.md 模板為什麼 Intent/Boundaries 是六個必填欄之二:它們不是寫給人看的裝飾,是 Task Context Packet 唯一的取材來源;缺欄 = 派工 prompt 少一塊,worker 只能自己猜。

派工 prompt 另有硬性禁令(圍欄④,見下節表):不得塞完整討論逐字稿,只帶 4-spec Operational Context 的最小子集 —— 獨立 context 解決「知道太少」,圍欄④解決「知道太多」,兩者互補 不互相取代。

6. Stop 與壓縮:為什麼文件是正本

Stop 之後(以及更關鍵的 PreCompact/PostCompact)—— 上下文超過門檻會被壓縮,壓縮做的事情是裁剪:已展開的 skill 本文會被裁掉, 被裁後不會自動重新展開,而 skill 描述清單(見上方 1)也不會因為壓縮而重新整批注入。 換句話說,session 記憶是會退化的 —— 這一輪還記得的細節,壓縮之後可能就不在了, 而且退化前後對使用者長得一樣正常。

這正是 6-implementation-notes.md「即時記帳」這條紀律的 runtime 理由:Progress Log、 Decisions、Self-Review 要在動作發生的當下就寫進 md,不能靠「等一下再一起補」——因為「等一下」可能 跨過一次壓縮,腦內記憶會消失但檔案不會。md 是唯一正本,對話不是契約,原因不是 流程潔癖,是壓縮這一格真的會把沒落檔的東西吃掉。

⑧ 大案與切片

這章要你懂:「案子很大」不等於「可以切」 —— 大小只是要你回頭評估的訊號, 真正的門檻是有沒有合法接縫。沒有接縫就不切,硬切出來的片會互相咬住。

上排兩份全片共用、只做一次;下排每片各走一條完整的 4→7,各有自己的 G2/G3。 片 A 到片 B 的那條線不是「執行順序」而是契約凍結順序 —— 後片只能依賴前片對外產出。

大案先評估切片可行性:≥3 個可獨立 phase、Diff Budget >15 檔、跨 repo, 都是「可能需要切片」的訊號,不是強制切片條件,也不證明已有合法接縫。

合法接縫

只能在「後片單純依賴前片對外產出(介面/資料契約), 不依賴其內部設計」的架構邊界切;不得只按數量平分,repo 分開也不自動是接縫。

軟訊號

單份 4-spec >~40 條 scenario,或 reviewer 預判一次審不動, 也要回頭評估切片;仍不能跳過合法接縫判準。

無接縫時

若拆分會讓後片依賴前片內部設計,保留單一 4 → 5 → 6 → 7 管線。

有合法接縫時,1-discussion/2-decision 全片共用;每片各走 4-spec → 5-tasks → 6-notes → 7-review,各有 G2/G3。每片 frontmatter 明載 parent,R/S ID 跨片不重號,並依片序凍結前片對外契約;前片契約改動時, 後片必須 impact review。

長時間與跨 session 依 STATUS.md、5-tasks.md、 6-implementation-notes.md 接力;無人看管的多 phase orchestration 屬專案層選擇, dev-flow 不依賴也不規範它。完整規則見 README §13–14。

新 clone／新機器打一次 dev-setup 重建這棵樹的 SQLite 快取。 已經在用的機器 git pull 把 .dev-flow/ 拉下來就夠，不必再跑 setup。 舊的 CONTEXT.md → dev-memory.py migrate-legacy，落地是候選，不是已確認。
