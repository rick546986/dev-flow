## 通用規則:已裁決項目佔不佔 §4 的額度?

**佔。** owner 裁決只解除 §4 篩選第 3 條的**排除**(「大規模重構或推翻既有架構決策
一律不做」),不解除第 2 條的**額度**(一輪最多 3 條)。

理由:額度存在的目的是「讓這個 commit 還 review 得動」,這個理由不會因為 owner
點頭而消失。一輪塞三個架構級改動,GPT 那側也審不動,反而讓下一輪的 finding 品質變差。

## 2026-08-21 · 第一批(解除連續 3~7 輪未決的三條)

三條一起裁,因為後兩條是同一個形狀(機器可讀的 verdict 宣稱得比實際證明到的更強),
拆開修會生出兩套不一致的語意。**但依上面的通用規則,它們仍各自佔一條額度。**

### D-1 · `GPT-P0-WORKTREE-SHARED-STORE` — 採選項 (a):runtime DB 改 per-worktree

**裁決**:本機 runtime SQLite 改成 **per-worktree**。記憶**內容**的共用走
`.dev-flow/` + git,不靠共用同一份可變檔案。

**owner 對「多 worktree 共用」的定義**:要的是「兩個 worktree 都看得到同一批已確認
的知識」,**不是**「兩個 worktree 讀寫同一份 SQLite 檔」。前者本來就是 `.dev-flow/`
的設計目標,後者從來不是需求。

**為什麼不選 (b) 全表加 scope 欄位**:scope 要散到每一條查詢與每一個唯一性約束上,
**漏一條就是靜默的跨 branch 污染**,而且沒有機械手段保證不漏。(a) 把 SQLite 降級成
worktree 本地快取,與既有設計宣告的「刪掉可從 `.dev-flow/` 重建」一致。

**為什麼不選 (c) fail-loud 拒絕多 worktree**:直接違反 owner 的實際需求(要能多
worktree 並行工作)。

**已接受的代價**:`AGENTMEM_HOME` 底下的目錄佈局會變,屬使用者可見行為變更。
owner 明確接受。

**附帶效果**:並行寫入問題在 SQLite 這一層**從根本消失**(沒有共用的可變檔案,
不需要加鎖)。`.dev-flow/` 那一層的並行寫入沿用本 repo 既有紀律 ——
`scripts/history-append.sh` 那套「目錄鎖 + 重試 + 只追加」,不要重新發明。

### D-2 · `GPT-P0-REMOTE-ATTESTATION-UNSOUND` — 採選項 (b):弱化成誠實欄位

**裁決**:不再宣稱跨機器物理耐久性。拆成實際證明得到的欄位,
例如 `remote_ref_matches`(遠端 ref 等於本機 HEAD)與
`preflight_not_known_local`(預檢時解析到的位址不在已知本機位址集合裡)。
`durable-check` 的 verdict 不得再暗示它是「連線本身」的強證明。

**為什麼不選 (a) 接管 Git 實際連線目標**:那是傳輸層重新設計,不是「小而對」的修法。
未來要做可以單獨排一輪。

**為什麼不選 (c) 維持現狀 + 補文件**:一個已知的 false-positive 路徑本身就是這道
barrier 的正確性缺陷,文件不會讓假證明變安全。GPT 這一點是對的。

### D-3 · `GPT-P1-LOCAL-ONLY-PASS` — 新增獨立的 verdict 值

**裁決**:新增 `LOCAL_ONLY_PASS`(或等效的強制性 durability-level 欄位),
讓「本機檢查過、遠端刻意跳過」與「遠端真的觀察過」在機器可讀層面分得開。

**與 §7 的關係(重要,一併定義)**:契約 §7 第 6 步的**通過集合只有 `PASS`**;
`LOCAL_ONLY_PASS` **不**滿足那道關卡。理由:`--local-only` 跳過的正是「觀察遠端」
那一步,連 `remote_ref_matches` 都拿不到,而那道關卡存在的唯一目的就是證明東西
真的推上去了。

**為什麼 D-2 + D-3 不會讓 §7 死鎖**:D-2 拿掉的是「跨機器物理位置」的宣稱,
而 §7 這道關卡真正需要的是 `remote_ref_matches` —— 那件事**可以機械證明**,而且
§7 第 5 步(`git fetch` 後比對 `HEAD` 與 `origin/<branch>`)本來就已經獨立驗過。
所以誠實化之後關卡照樣過得了,只是它宣稱的東西變成它真的證明得到的東西。

**實作順序建議**:D-2 與 D-3 動的是同一個 verdict 契約,同一輪一起做;
D-1 動的是 store/路徑層,另一輪。不要三條塞同一輪(見上面的額度規則)。

## 2026-08-21 · 第二批(首輪 automation 提出的新項目)

### D-4 · entity-only 的 CURRENT 查詢 — 採選項 (b):envelope 加非破壞性明細欄位

**問題**:查詢指名 entity 但完全沒指名 fact_key 時,回傳該 entity 底下全部 fact
並取最嚴重狀態。呼叫端看到 `NEEDS_VERIFICATION` 分不出「被問的那筆是 STALE」與
「別筆是 STALE、被問的那筆其實 OK」。

**裁決**:選 (b) —— envelope 增加一個**非破壞性**的 `per_coordinate` 明細欄位。
既有欄位語意一個字都不准動;呼叫端想細分就讀新欄位,不讀就跟現在完全一樣。

**為什麼不選 (a) 維持現狀**:agent 指出的資訊損失是真的,而且它剛好是這一輪修掉的
那個 bug 的近親 —— 兩者都是「把多個座標壓成一個結論,壓完就分不出來源」。修了一半
留一半,下次還會再撞。

**為什麼不選 (c) 退到歧義語意**:會打爛 eval(`current_truth_accuracy` 門檻 1.0),
而 entity-only 是正常問法不是歧義。agent 自己也不建議。

**實作約束**:
- 新欄位**必填且明確**,不要用「有就給、沒有就省略」——
  選填加 `.get()` 等於讓 `None` 靜默當成空,這正是本輪 durable 記下的那個教訓。
- 既有 eval 23 案的數字**一個都不准變**。變了就是改到既有語意,退回重做。
- 依通用規則,這條佔一條 §4 額度。

**優先序**:排在 D-1(`GPT-P0-WORKTREE-SHARED-STORE`)**之後**。D-1 是唯一剩下的
P0,D-4 是 P1 且有明確的非破壞性做法,不急。
