## 採納並修好的 finding

### ①[P1] event 的耐久性在「append 成功、local 還沒前進」的視窗不冪等 —— **成立,已修**

**它指的位置**:`memory/agentmem/sync.py::consolidate()` /
`memory/agentmem/durable.py::append_events()`。

**我查證到的根因**(不是照抄它的說法):

它的判斷是對的,而且它指出的是**上一輪修法的邊界**,不是上一輪漏改一行。
上一輪把「先寫檔、才動 local 狀態」這條順序套到 fact 與 event 上。那條順序對
`write_state()` 是**充分的**:它是 deterministic 整檔取代,寫完後行程死掉,
重跑寫的是同一份內容取代同一個檔 —— 它收斂。

`append_events()` 不是同一種 writer。`durable.py:431` 是 `open(path, "a")`,
而 **JSONL 不是 keyed storage**。所以順序修好之後剩下的視窗是不對稱的:

```
append_events 成功        ← .dev-flow/ 已經有 evt_X
↓  行程死掉 / SQLite 失敗
store.add_event(durable=True)
store.set_candidate_status(CONSOLIDATED)
```

候選留在 CONFIRMED(這是對的,重跑才補得回來),但重跑會把同一個 `event_id`
**再 append 一次**。

這裡有一件我認為比它的敘述更精確的區分,也是修法的依據:
**deterministic id 是去重的「依據」,不是去重的「機制」。** 上一輪引入
`_derived_id()` 讓重試拿到同一個 id,那對 fact 就夠了(因為 `upsert_fact` 是
`ON CONFLICT(fact_id)`,keyed);對 JSONL 不夠,因為沒有任何東西拿那個 id 去比。

順著查出**兩個它沒提到**的相關缺陷:

1. **revision 的 `event_id` 是隨機的。** `sync.py:452` 是
   `record.setdefault("event_id", ids.new_id("event"))`。就算 `append_events`
   會去重,隨機 id 也讓去重永遠對不上 —— 同一次 supersede 會在
   `.dev-flow/events/` 累積成 N 筆,每一筆都聲稱是它。修 ①如果只改
   `append_events`,revision 這條路仍然是壞的。
2. **`open(path, "a")` 中途斷電會留下半行**,而半行讓整個檔案之後都讀不出來
   (`iter_events` 對壞行 fail-loud,這是對的)。原子取代同時解掉這一件 ——
   它不是額外的加分項,是同一個修法的必然結果。

### ②[P1] `verify/reverify` 的新 Current Truth 只活在本機 —— **成立,已修**

**我查證到的根因**:比它的敘述更具體一層。`checkpoint()` 只在
**CONFIRMED fact 候選**進 `consolidate()` 時才把 entity 加進 `entities_touched`
→ 才 `write_state()` 整檔寫回。而 `truth.reverify()`(公開 CLI
`verify --observed`)**不建候選**:它直接 `upsert_fact` 舊列標 SUPERSEDED、
插入新的 VERIFIED 列、記一筆 pending revision。於是沒有任何東西會把那個
entity 加進來,`.dev-flow/state/` 停在舊值。

真正的修法選擇在這裡,而它值得被質疑:

GPT 建議「讓 `reverify()` 走既有的 candidate/consolidation 協定」。我**沒有**
那樣做,理由是那會產生第三筆 fact:`consolidate()` 的 fact 分支會用
`_derived_id("fact", candidate_id)` 再 `upsert_fact` 一次,而 `reverify` 已經
用 `ids.new_id("fact")` 插了新列 —— 兩個 id 指同一件事。

我改的是**判準**:`facts.durable` 這個欄位本來就存在,而
`promote_entity_facts()` 寫檔成功後會把它設成 1。所以它的語意本來就是
**「這一列現在的內容就是 `.dev-flow/` 裡的那份」**。缺的只是兩件事:

1. `reverify()` 改動內容時沒有把旗標打回 0(舊列被標 SUPERSEDED 卻仍
   `durable=1`,而檔裡還寫著 VERIFIED —— 那是一句沒有憑據的「已耐久」);
2. `consolidate()` 從來沒去看這個旗標。

這個判準比「列舉有哪些路會改 fact」強,而那正是我選它的原因:列舉的寫法要求
每個新增寫入路徑的人記得回來改 `consolidate()`,而**忘記是靜默的** ——
這一題本身就是忘記的產物。

順著補上第三件它沒提到的:`durable_check()` 只檢查 pending **revision**。
「歷史沒落地」與「**現況**沒落地」是兩件事,只報前者的話,
「revision 寫成功、現況檔沒重寫」會判 PASS。新增第⑤項 `FACT_STATE_NOT_REWRITTEN`。

### ③[P1] git status 解析不完整仍能回 `OK` Current Truth —— **成立,已修,但範圍與它建議的不同**

**我查證到的根因**:parser 拒絕猜、把讀不懂的欄位原樣回報成
`snapshot["status_unparsed"]`(`identity.py:374`)是對的,但那份不確定性到
`resolve_current()` 就斷了 —— 它只讀 `dirty_files`。

**我不同意它的修法範圍,這一條請 review 反駁我**:

GPT 說「if status is UNKNOWN and current fact depends on workspace cleanliness,
force `needs_inspect=True`」。照字面做會蓋掉這個 codebase 既有的一條規則,
而那條規則有明確理由(`truth.py:240-249`):**指紋相符時 dirty 不得把 fact
打回 STALE**,否則 reverify 之後 fast path 永遠不可達(開發中的工作樹幾乎永遠
dirty)。

我查證後的結論是:指紋記的是「驗證時看到的內容」。**內容仍與指紋相符 =
我們驗過的正是現在這一份**,而 git 看不看得懂它的狀態列與那件事無關。rename、
刪除、內容變更全都會讓指紋不符而被抓到。所以不確定性真正吃掉的只有 dirty
那一條路:

> 解析不完整 = dirty 清單不完整 = **沒有指紋可比的依賴無法證明乾淨**。

範圍就落在這裡,不多不少。指紋齊全的 fact 不受影響 —— 把它一起打回 STALE
是拿一個無關的訊號否定已經驗過的內容。

**這也讓我在中途改掉了自己的 fixture,值得記一筆**:第一版測試用
`fingerprints={}` 的 fact,結果它**在舊實作下就已經不走 fast path**——
`resolve_current` 的 `if not stored` 會先把它降級成 CANDIDATE。那個 fixture
測不到這個缺口。真正的缺口在**混合**:一個依賴有指紋、另一個沒有 →
`stored` 非空 → fast path 可達 → 沒指紋的那個只剩 dirty 能證明它乾淨。
換成混合 fixture 之後才真的紅。

**「舊實作下測試真的紅」的證據**:新增 7 案,**5 案實紅**:

## 需要 owner 裁決

### ① shared project DB vs branch/worktree 一致的 durable view(GPT [P0],連兩輪未解)

縮小(例如「branch 隔離只保證 implementation facts」)並補一個把該行為寫下來
的測試 —— 後者也是一個合法答案,而且成本最低。

### ② 「沒有 `event_id` 的 event 一律拒收」是否可接受
