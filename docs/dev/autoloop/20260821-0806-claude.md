## 採納並修好的 finding

### ①[P1] GPT-P1-CURRENT-TARGET-SCOPE —— `_fact_targets()` 不是真的座標精確匹配,共用 fact_key 的不相關 entity 會污染 CURRENT 狀態 —— **成立,已修**

**它指的位置**:`memory/agentmem/query.py::_fact_targets()`(上一輪
`GPT-P1-CURRENT-500` 修的同一支函式)。

**我查證到的根因**:成立,親自重讀 `_fact_targets()` 逐行確認。上一輪只移
除了前置筆數視窗(`limit=None`),比對邏輯本身沒有動——原邏輯是三個條件
互相獨立 OR:

```python
hit = any(e and e in haystack for e in entities)   # ①query symbol 命中「整串」haystack
if not hit:
    hit = textnorm.normalize_symbol(row["entity_key"]) in query_norm \
        or textnorm.normalize_symbol(row["fact_key"]) in query_norm  # ②③
```

其中 `haystack = entity_type + entity_key + fact_key + value` 全部串接後
正規化。問題:條件①只要求「查詢裡抽出的某個 symbol 出現在這一整串裡」,
不要求命中的是 `entity_key` 這個座標分量——如果兩個 entity 共用同一個
`fact_key`(例如 `database.lab-order.current_table` 與
`database.audit.current_table`),查詢裡的 symbol `current_table`
(從 `textnorm.symbols()` 抽出,不含 `lab-order`,因為 hyphen 不在任何
symbol pattern 裡)會同時出現在**兩個 entity** 的 haystack 裡,條件①對
兩者都成立——條件③(`fact_key` 直接出現在查詢文字裡)本來就會讓沒被指名
的 entity 也命中,但這裡其實連條件③都不必跑到,條件①自己就已經污染了。
`_current()` 對多筆座標取「最嚴重狀態」(`CONFLICT > NEEDS_VERIFICATION >
OK`),所以沒被指名的 `audit`(CANDIDATE/STALE)足以把明確指名且已
VERIFIED 的 `lab-order` 答案拖成 `NEEDS_VERIFICATION`——GPT 給的例子完全
可重現,不是理論推演。

**「舊實作下真的紅」的證據**(`test_query.py::ExecutionTest`,新增 3 案,
2 案在舊實作下實紅):

```
test_current_target_scope_excludes_unnamed_entity_with_same_fact_key
  AssertionError: 'NEEDS_VERIFICATION' != 'OK'
test_current_target_scope_excludes_unnamed_entity_when_stale
  AssertionError: 'NEEDS_VERIFICATION' != 'OK'
```

治具:setUp 已有 `database.lab-order.current_table = lab_order`
(`VERIFIED`)。新測試各自額外插入
`database.audit.current_table = audit_log`(一個 `CANDIDATE`、一個
`STALE`),查詢「目前 lab-order 的 current_table 是什麼?」——明確指名
`lab-order`,舊實作下仍因為 `audit` 共用 `current_table` 而被拖成
`NEEDS_VERIFICATION`,直接對上 GPT 給的重現路徑。第三案
(`test_current_target_scope_ambiguous_fact_key_without_entity`,查詢完全
不指名任何 entity,只給共用 `fact_key`)在舊實作下**沒有**變紅——舊邏輯
剛好也會落在 `NEEDS_VERIFICATION`(不是它宣稱的「安全」,是因為 fuzzy
search fallback 恰好給出同樣的狀態),但這不代表沒有缺陷:它是靠巧合避開
斷言,不是靠設計保證不會悄悄選一個 entity 當答案,所以照樣一併修,不因為
它沒紅就跳過。

**修法**:`_fact_targets()` 改成先算出查詢文字裡「有指名到哪些目前存在的
`entity_key`」(`entity_named`,用 `entity_key` 正規化後的字串是否為查詢
正規化字串的子字串,或等於某個抽出的 symbol);

- `entity_named` 非空 → candidate 座標**限定**在這些 entity 底下,不論其
  他 entity 是否共用 `fact_key`/`value` 文字(蓋掉原本條件①③的跨
  entity 污染路徑)。
- `entity_named` 是空的(查詢完全沒指名任何目前存在的 entity)→ 才退回靠
  `fact_key`/`value` 反查;如果命中結果落在不只一個 entity 上,視為歧義,
  回空 target 列表,不悄悄選一個當答案。

`_search()`(模糊探索式檢索)完全不動——這條 finding 一樣不屬於它的範圍。

**萃取**:1 筆進 durable ——
`knowledge/invariants/current-target-must-be-scoped-to-a-named-entity-`
(CURRENT target 生成必須用「查詢有沒有指名這個 entity」當篩子,不能只靠
共用的 fact_key/value 做跨 entity 的 OR 比對;跟上一輪
`relevance-cap-must-come-after-not-before-exact-match` 是同一支
`_fact_targets()` 裡兩層不同根因——一個是筆數視窗污染精確匹配,一個是
跨座標 OR 污染精確匹配)。走 `dev-talk`(propose → confirm → checkpoint →
end),`promoted: 1`,`revisions: 0`。

## 給 GPT 的下一輪輸入

**最該被挑戰的設計決策:**

1. **「entity 完全沒被指名時,fact_key/value 命中落在不只一個 entity 上就
   回空 target,退到模糊檢索」是我這輪選的歧義處理方式,不是唯一可能的
   設計。** 我沒有讓它回傳一個明確的「ambiguous / 多目標」信號給呼叫端
   (那需要改 envelope 契約,屬於第 8 節「修法會改變公開 API」的紅線,這
   輪不做)。如果你認為「悄悄退到 NEEDS_VERIFICATION/模糊檢索」本身也算
   一種隱性降級(呼叫端看不出這跟「有一筆 STALE」的 NEEDS_VERIFICATION是
   兩種不同原因),請具體說明對呼叫端會造成什麼實際傷害,而不是只重申
   「應該要有明確的 ambiguous 語意」。
2. **「entity 被指名時,回傳這個 entity 底下**全部**的 fact,不只是查詢字
   面提到的 fact_key」是我延續原有行為(`test_mixed_verified_and_stale_
   is_needs_verification` 依賴這個語意——同一個 entity 的多筆 fact 混合
   VERIFIED/STALE 時,整體要降級)。這輪沒有重新檢查這個「entity-only 一
   律回全部 fact」的語意本身有沒有另一種污染路徑(例如一個 entity 底下有
   10 筆 fact,查詢只問其中一筆,但另外 9 筆的狀態照樣拖累整體)。如果你
   認為這個既有語意本身也需要收緊,請指出具體的重現場景。

**我不打算改的方向與理由(省下重複建議):**

- **這輪的修法只改 `_fact_targets()` 的候選篩選規則,不改 `_current()`
  的狀態聚合邏輯(取最嚴重狀態)本身。** 聚合邏輯本身是對的(§P0-4 契
  約),問題出在餵給它的候選集合摻了不該摻的 entity,不是聚合規則錯。
- **不索引化 `entity_key`/`fact_key` 查詢(`GPT-P2-CURRENT-FULL-SCAN`)。**
  這條已經列進「本輪未處理」,理由是正確性邏輯這輪剛改完,不在同一輪疊
  加效能改動去混淆驗證范围。
