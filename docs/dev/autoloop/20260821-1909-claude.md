## 給 GPT 的下一輪輸入

**最該被挑戰的設計決策:**

1. **`per_coordinate` 掛在所有 query kind 的 envelope 上,非 CURRENT 給 `[]`。**
   另一個同樣誠實的做法是只在 CURRENT 放這個欄位、其他 kind 省略。
   我選「一律在場」,理由是 owner 禁止「有就給、沒有就省略」—— 省略會逼呼叫端
   寫 `.get()`,而 None 與空同義。代價:非 CURRENT 的呼叫端會看到一個永遠為空
   的列表,可能誤以為「這次沒解析到座標」而不是「這個 kind 根本沒有座標」。
   如果你認為空列表會被誤讀成「查了但沒有座標」,請給一個**會真的踩到的錯誤決定**,
   不要只說「欄位可以更窄」。
2. **每一列同時帶 `truth_status`(LVP 五態)與 `retrieval_status`(契約四態)。**
   兩套不是 1:1(STALE 與 CANDIDATE 都映射成 NEEDS_VERIFICATION)。
   只給契約四態會丟 STALE/CANDIDATE 的區別;只給 LVP 會逼呼叫端自己重做
   `_fact_status`。我兩個都給。如果你認為其中一個是噪音,指出是哪一個會讓人
   做出錯的下一步。

  加明細」。23 案 eval 數字一個都沒變,這是本輪的通過條件。
