**我查證到的根因**:

## 刻意不做的 finding

### GPT-P1-LOCAL-ONLY-PASS —— `--local-only` 與遠端已驗的 PASS 共用同一個 `verdict` 字串

**它說什麼**:`durable_check(local_only=True)` 成功時 `verdict` 一樣是純
`"PASS"`,只有 `remote_observed` 這個欄位能分辨兩種狀態;只看 `verdict` 或
`cmd_durable_check` 的 exit code 的呼叫端會把兩者混為一談。

**我查證到的**:成立。讀了 `sync.durable_check()` 與 `memory/dev-memory.py::
cmd_durable_check()`——後者的 exit code 就是 `0 if result["verdict"] ==
"PASS" else 1`,對 `local_only` 兩種狀態完全一樣。

**為什麼這一輪不做,而不是直接選一個修法**:

`verdict` 是這支公開 CLI 已經在用的 JSON 欄位,現在的值域就是
`{"PASS","FAIL"}`。GPT 給的兩個方向都會改變這個值域看起來的樣子:

- 方案一(三態 `PASS_REMOTE`/`LOCAL_ONLY`/`FAIL`):任何現有腳本如果做
  `jq -r .verdict` 比對字面 `"PASS"`,在 `--local-only` 這條路上的行為會
  改變——即使 CLI 自己的 exit code 我可以同步放寬去接受新字串,JSON 消費端
  未必是這支 CLI 自己。
- 方案二(保留 `verdict`,只加一個更嚴格的 `durability_level` 欄位):
  不改變既有值域,但它的價值取決於「有沒有一個更嚴格的呼叫端真的去檢查那
  個新欄位」——而這個 repo 目前唯一實際依賴 durable-check 輸出的呼叫端就是
  這份 autoloop 自己的收尾程序,它已經在讀 `remote_observed`(見上一輪與
  這一輪的接續紀錄都明寫這個欄位),不是只看 exit code。

這個決定的核心不是「要不要修」,是「往哪個方向改一個既有公開 CLI 的 JSON
契約」——對應第 4 節「修法會改變公開 API 或使用者可見行為,而不只是修正
錯誤」。兩個方向我都同意是合理的,但選哪個、或兩個都不選只加一段更醒目的
人類可讀警示,是 owner 該看一眼的事,不是自動迴圈單方面決定。寫進下面
「需要 owner 裁決」。

   可能在某些容器/網路設定下一無所獲(回空 `frozenset`)。這種情況下
   loopback/link-local/unspecified 三類還是擋得住,但「解析後等於這台機器

   `_local_machine_ips()` 查不到任何位址時會被漏放行。這是我自己在
   docstring 裡承認的已知降級,但沒有做「查不到本機位址就整個 fail
   closed」——那樣做的代價是任何 UDP 探測失敗的環境都會讓所有真實遠端的
   durable-check 判 FAIL,我認為那個代價太大。請挑戰這個取捨。
2. **SSH config Host 別名重映沒做,只寫成殘留缺口。** 我判斷這是這一輪修法
   的自然延伸、下一輪可以直接做,不需要方向決策——請確認這個判斷,如果你
   認為它其實跟 worktree 隔離一樣需要先決定策略(例如要不要在沒有 `ssh`
