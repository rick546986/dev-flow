### ②[P0] GPT-P0-REMOTE-ATTESTATION-UNSOUND —— **依 owner 裁決 D-2 選項 (b) 修完**

**我查證到的根因**:成立,而且是兩個獨立的問題被同一個 verdict 蓋住。
`_local_machine_ips()` 是 best-effort、非空也可能不完整 —— 對一個不完整集合做
**否定成員測試**,結論只能弱到「不在**已知**集合裡」,不是「在別台機器上」。
再加上 SSH config 的 `HostName` 重映不在偵測範圍內,而且預檢解析到的位址與
後續 Git transport 實際連上的位址之間**沒有綁定**(中間可以換掉)。
`ls-remote` 成功 + SHA 相等證明的是有用但嚴格較弱的一句話。

**修法(裁決 (b),不做 (a) 的傳輸層重新設計)**:把證據拆成兩個**必填**欄位
誠實回報 —— `remote_ref_matches`(伺服器回報的 ref 等於本機 HEAD,可機械複驗)
與 `preflight_not_known_local`(預檢解析到的位址不在**已知的**本機位址集合裡)。

verdict 不再宣稱跨機器物理耐久性,docstring / README 同步改寫。

**必填而非選填**,理由寫進 docstring 與守衛訊息:選填會讓呼叫端寫
`result.get("remote_ref_matches")`,而 `None` 在布林語境下與 `False` 同義 ——
少一個欄位就靜默降級成「當它沒證明」或「當它證明了」,取決於呼叫端怎麼寫,
而不是取決於實際證據。

### ③[P1] GPT-P1-LOCAL-ONLY-PASS —— **依 owner 裁決 D-3 修完**

**我查證到的根因**:成立。`--local-only` 走 `rev-parse <upstream>`,那是**本機
快取**,所以 `pushed` 會是 `True` 而伺服器從頭到尾沒被問過。舊契約讓這種情況與
「真的觀察過遠端」共用同一個 `PASS`。

**修法**:verdict 三值 `PASS` / `LOCAL_ONLY_PASS` / `FAIL`,而且**由證據推導、
不由呼叫端傳進來的旗標推導** —— 判斷式是 `elif remote_ref_matches:`,不是
`elif not local_only:`。這一點不在裁決文字裡,是我加的:旗標說的是「呼叫端要求
了什麼」,欄位說的是「實際拿到什麼證據」,只認後者才 fail-closed —— 未來若多一
條也拿不到遠端證據的路徑,它自動落在 `LOCAL_ONLY_PASS`,不必記得多加一個分支。

**CLI 退出碼:兩種 pass 都退 0。** `--local-only` 是呼叫端明確要求的合法用法,
讓它退非零等於逼人忽略退出碼。退出碼只有兩個值、承載不了三值語意,所以需要強
保證的關卡必須讀 `verdict` 或 `remote_ref_matches` —— 契約 §7 第 6 步的通過集合
只有 `PASS`,正好就是這樣消費的,本輪自己走過一次(見驗證結果最後一列)。

**「舊實作下真的紅」的證據**(`test_durability_barrier.py` 新增
`DurableVerdictHonestyTest` 7 案,**舊實作下 7 案全紅** —— 2 failures + 5 errors):

FAIL: test_verdict_dict_always_exposes_the_honest_fields
  AssertionError: 'remote_ref_matches' not found in {...}

**既有兩案的斷言我改了,而且這不是「改測試讓現況變綠」**:
`test_local_only_is_explicit_and_says_so` 與
`test_local_only_still_passes_without_claiming_remote` 原本斷言
`verdict == "PASS"`,改成 `"LOCAL_ONLY_PASS"`。那個斷言本身**就是**這次契約變更
的內容(D-3 的全部內容就是「這個情況不准回 PASS」),而且改的方向是變嚴、不是
變鬆:原本兩種強度共用一個值,現在分開。§4 第 6 條禁的是「實作沒改、只改測試
去迎合現況」,這裡實作先改、測試跟著契約走。
