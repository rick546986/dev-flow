### ①[P0-1] `durable-check` 收本機 remote 當「離開這台機器」的證據 —— **成立,已修**

**它指的位置**:`memory/agentmem/sync.py::_observe_remote()`。

**我查證到的根因**(不是照抄):

它的判斷成立,而且我同意它對契約的讀法。上一輪把「問遠端本身」修好了
(`ls-remote` 取代 `rev-parse origin/<branch>`),但那只回答了一句**嚴格較弱**
的話:「設定的 upstream 連得上,而且有這個 commit」。而程式與文件從頭到尾寫的
是另一句:「記憶離開這台機器了嗎」。

一個 git remote 不必然在別台機器上。`/Volumes/backup/mirror.git`、
`file:///Users/rick/mirror.git`、`ssh://git@localhost/repo.git` 三者都會讓
`ls-remote` 回報正確的 SHA,於是 `verdict=PASS`、`remote_observed=true` ——
而硬碟壞掉時它們跟工作樹一起消失。判定聲稱了一件它沒有驗證的事。

GPT 沒提到、而我查證時發現的第三個落點,決定了修法的形狀:

**只讀 `remote.<name>.url` 是不夠的。** `url.<base>.insteadOf` 會在連線時把
設定檔裡的 URL 改寫掉。實測確認(不是憑印象):

```
remote.origin.url         = ssh://git@remote.test/x.git
url.<localpath>.insteadOf = ssh://git@remote.test/x.git
git ls-remote --get-url origin  →  /tmp/…/b.git
```

也就是說,只看設定檔字面值的話,一個實際只寫到本機目錄的 remote 可以掛著網路
形狀的名字通過判定。所以判的必須是 **`ls-remote --get-url` 解析後**的 URL ——
那是 git 實際會連上去的那一個,而 `--get-url` 不連網。

### ②[P1-2] WHY / HOW 用「最近 200 筆」撈已知主鍵 —— **成立,已修**

**它指的位置**:`memory/agentmem/query.py::_why()` / `_how()`。

**我查證到的根因**:

```python
row = next((d for d in store.decisions(limit=200)
            if d["decision_id"] == hit["item_id"]), None)
```

拿一個**已知的主鍵**去掃「最近 200 筆」。檢索索引沒有那個視窗,所以命中一筆
更舊的 decision 時 `row` 是 `None` —— 而 `_why()` 仍然把它算成 decision、
仍然回 `retrieval.OK`。

我認為比它的敘述更關鍵的一句是:**這不是排序問題,是契約問題**。WHY 的答案不是
「有一筆 decision」,而是它的 `reason` / `alternatives` / `tradeoff`;HOW 的答案
是 `steps` / `verification`。回 `OK` 卻沒附上那些欄位,等於系統聲稱它有可靠答案
而實際上沒有 —— 那比查不到更糟:查不到會回 `NO_RELIABLE_MATCH`,呼叫端知道要
去問人;回一個空殼的 `OK`,呼叫端會拿它當答案。這與本專案「CURRENT 找不到
verified fact 時回 NEEDS_VERIFICATION 而不是把旁證包成 OK」是同一條紀律的另一個
落點,而這裡漏了。

`_why()` 的 `evidence` 也一起遺失(`json.loads(row["evidence_json"])` 在
`if row:` 裡),所以「答案沒有證據」與「答案沒有內容」同時發生。

**「舊實作下真的紅」的證據**(`HydrationIsByPrimaryKeyTest`,新增 5 案,
**5 案全紅**):

| 測試案 | 舊實作下的實際輸出 |
|---|---|
| `test_why_hydrates_a_decision_outside_the_recent_window` | `None != '兩邊欄位重疊九成'` |
| `test_why_ok_always_carries_the_reason_fields` | `'reason' not found in {…}`(hit 有 title/score,沒有 reason) |
| `test_why_evidence_comes_from_the_hit_row` | `{'type': 'adr', …} not found in []` |
| `test_how_hydrates_a_skill_outside_the_recent_window` | `None != ['跑 migration', '重啟 worker']` |
| `test_row_lookup_by_primary_key_does_not_depend_on_recency` | `AttributeError: 'Store' object has no attribute 'decision_row'` |

每一案都先斷言「目標真的在視窗外、而檢索真的命中它」(260 筆更新的無關紀錄
把它推出去),否則測的不是這件事。

**修法**:`store.decision_row(decision_id)` / `store.skill_row(skill_id)`
兩支主鍵查詢(對稱於既有的 `knowledge_row` / `fact_row`),`_why` / `_how`
改成直接撈。沒有動 `decisions()` / `skills()` 的預設 `limit` —— 要列表的呼叫端
本來就要視窗,問題從來不是那個預設值,是「拿已知主鍵去掃列表」這個動作。

**新守衛(含變異驗證)**:`check-memory-architecture.sh` 新增
「WHY/HOW 的內容用主鍵撈」,同時釘兩件事(不得出現
`store.decisions(limit=N)` 形狀、必須出現 `decision_row` / `skill_row`)。
負向案 `MEM-26` 把 `next((d for d in store.decisions(limit=200) …))` 放回去
→ 守衛紅(已驗)。

## 刻意不做的 finding

### [P2] durable event log 讀取/rebuild 時不主動驗重複 event_id

**它說什麼**:`_existing_events()` 把 `event_id → canonical payload` 收成 dict,
舊檔裡若已有同 id 同內容的重複行,dict 表示會把它折疊掉,`rebuild_local()`
的 `ON CONFLICT(event_id)` 又在 local 側再折一次,於是舊的損壞被靜默正規化。

**為什麼這一輪不做**:它的技術判斷成立,但它建議的兩條路都超出「修缺陷」:
「fail loudly」會讓既有使用者的 `.dev-flow/` 在下一次 `rebuild` 時整批拒絕載入
(使用者可見行為的改變,而且是最糟的那種時機);「expose a repair command」是新
的公開 CLI 子指令。兩者都該被 owner 看一眼,而不是由自動迴圈在一輪裡決定。
對應第 4 節「修法會改變公開 API 或使用者可見行為,而不只是修正錯誤」。

它也**不是**進行中的資料遺失:重複 append 的那個缺陷上一輪已經修掉,現在的
寫入路徑不會再產生同 id 的第二行。這一條的價值是**偵測歷史損壞**,優先序低於
會產生新錯誤的缺陷。留在「本輪未處理」。
