## 採納並修好的 finding

### ①[P0] GPT-P0-LOCAL-IP-INVENTORY-FAILOPEN —— 本機介面位址列表拿不到時,`ip_is_offmachine` 仍可能誤放行 —— **成立,已修**

**它指的位置**:`memory/agentmem/identity.py::ip_is_offmachine()` 與
`memory/agentmem/sync.py::_observe_remote()`。

**我查證到的根因**:成立,而且是「不理論」的真缺陷,不是邊角案例。
`ip_is_offmachine(raw_ip, local_ips=None)` 在 `local_ips` 為 `None`(即
`_observe_remote()` 呼叫時的預設用法)時會現查 `_local_machine_ips()`。那支
函式是 best-effort(`socket.getaddrinfo(gethostname(), None)` +
UDP `connect()` 讀 `getsockname()`),兩種探測手法都失敗時回空
`frozenset()`。`ip_is_offmachine` 拿到空集合後執行
`raw_ip not in local_ips` —— 空集合上這句話恆真,於是任何解析到的、非
loopback/link-local/unspecified 的位址都被判成「off machine」,即使那個
位址其實就是這台機器自己一個 `_local_machine_ips()` 沒探測到的介面。舊
docstring 自己寫「查不到也不會誤放行,只會少擋一種情境」——這句話在
`local_ips=None` 走現查路徑時是**錯的**:一路追下去,`_observe_remote()`
既沒有檢查 `_local_machine_ips()` 本身是否為空,也沒有把「查不到本機介面」
與「查到了、但這個位址不在裡面」分開處理,直接把兩者都當成「off machine」
的證據。

親自重現(`ip_is_offmachine("192.168.1.50", local_ips=frozenset())` →
`True`)確認 GPT 給的例子準確,不是誤讀。

**「舊實作下真的紅」的證據**(`test_durability_barrier.py::
RemoteEndpointAttestationTest.test_local_ip_inventory_failure_fails_closed`,
新增 1 案,舊實作下實紅):

```
AssertionError: 'PASS' != 'FAIL'
: {'verdict': 'PASS', ..., 'remote_observed': True, 'problems': []}
```

治具:`_remote_with_resolved_ips({"192.168.1.50"})`(主機名解析到一個看起來
像本機 LAN 介面的位址,同既有 `test_dotted_hostname_resolving_to_a_local_
interface_is_not_off_machine_proof` 那一案)再把 `identity._local_machine_ips`
patch 成回 `frozenset()`(探測全部失敗)。舊實作直接 PASS、`remote_observed:
true`——這正是 GPT 說的「不是理論上的」false PASS:一個完全沒有本機介面
證據的判定,聲稱記憶已經離開了這台機器。

**修法**:

1. `sync._observe_remote()` 在解析出 `ips` 之後,新增一次明確的
   `local_ips = identity._local_machine_ips()` 呼叫;`local_ips` 本身是空
   集合時直接 `return (None, REMOTE_UNVERIFIED, ...)`,不再把空集合當成
   「這台機器沒有任何位址」的正常結果傳給 `ip_is_offmachine` 比對。
2. 拿到非空的 `local_ips` 之後,顯式傳給每一次 `ip_is_offmachine(ip,
   local_ips=local_ips)` 呼叫(原來是 `ip_is_offmachine(ip)`,每個位址各自
   重新現查一次 `_local_machine_ips()`——除了多餘的重複探測,也讓「空集合」
   這個訊號在多次呼叫之間可能不一致;現在只查一次、共用同一份結果)。
3. `identity.py::_local_machine_ips()` 與 `sync.py::_observe_remote()` 的
   docstring 同步更正:明講「回傳空集合代表探測全部失敗,不代表這台機器
   沒有任何位址」,並點名這是 `GPT-P0-LOCAL-IP-INVENTORY-FAILOPEN`(已修)。

**不動的部分**:`ip_is_offmachine(raw_ip, local_ips=None)` 這支公開函式的
簽名、單元測試裡明確傳 `local_ips=frozenset()` 的既有案例(測 loopback /
link-local / unspecified 三類,那三類在函式一開頭就 return,不受這次改動
影響)全部原樣通過,見下方驗證。真正變的只是**呼叫端**(`_observe_remote`)
在「現查」這條路徑上多了一層 fail-closed 檢查——不是把 fail-closed 的責任
下放給 `ip_is_offmachine` 本身,那樣會讓它在被顯式傳入空集合的既有測試裡
(例如驗證 `192.0.2.10` off-machine 那幾案,如果哪天改成傳空集合)行為不
可預期。

**GPT 給的兩個必要回歸測試**,逐一核對:

1. 「Patch `_local_machine_ips()` 到 `frozenset()`,解析到非 loopback 位址,
   結果不得 PASS」——**已覆蓋**(`test_local_ip_inventory_failure_fails_closed`)。
2. 「Patch `_local_machine_ips()` 省略掉真正的本機 LAN 位址,同時解析結果
   剛好是那個位址,結果必須是 `REMOTE_UNVERIFIED` 或等價,不是 PASS」——
   **判斷這條測不出來,見下「查證後不成立的 finding」**。

## 查證後不成立的 finding

### GPT 必要回歸測試 #2(local_ips「非空但缺了某個真實介面」）—— 判斷做不到,不是忽略

GPT 原文:「Patch `_local_machine_ips()` to omit the actual local LAN address
while resolution returns that address; result must be `REMOTE_UNVERIFIED` or
equivalent, not PASS.」

我查證後判斷:這句話描述的是「`_local_machine_ips()` 回傳了**非空**但**不
完整**的集合」這個情境本身無法被系統自己偵測——`_local_machine_ips()` 只有
兩種探測手法(hostname 解析、UDP connect 讀 getsockname),兩者只要有任何
一個成功就會回非空集合;「回非空集合」在目前實作下**不可能**代表「探測
完整」,但系統本身也沒有辦法從一個非空但可能不完整的集合反推出「我還漏了
什麼」。GPT 自己在 Required fix direction 也承認同一件事:選項 2(可靠的跨
平台介面列舉)需要新依賴或 platform-specific syscall,在本專案 stdlib-only
/ floor 3.9 / 不新增依賴的範圍外(見第 4 節排除清單)。

我修的只是**空集合**這一種可以被系統自己識別、無歧義的「不完整」訊號
(兩種探測手法都失敗 = 我知道我不知道)。「非空但缺一個介面」是一種系統
自己分辨不出來的不完整(我不知道我不知道),沒有偵測手段就沒有修法,寫成
下面「刻意不做」而不是硬做一個測不出來的東西。

## 刻意不做的 finding

### GPT-P0-SSH-EFFECTIVE-ENDPOINT —— SSH config 的 Host 別名重映 —— 這一輪還是沒做

**它說什麼**:SSH remote 的實際連線目標由 `~/.ssh/config` 的 `HostName`
決定,不是我們解析的字面主機名;要堵這個需要 `ssh -G <host>` 拿到 SSH 實際
會用的 hostname。

**我查證到的**:成立,而且是上一輪(`20260821-0515`)自己在
`_observe_remote` docstring 裡明寫的已知殘留缺口,不是新發現。

**為什麼這一輪還是沒做**:不是方向不確定(上一輪已經判斷這是「同一個修法
的自然延伸,不需要先決定策略」),是這個容器裡**沒有 `ssh` 執行檔**
(`which ssh` 找不到)。我沒有辦法在這台機器上對真正的 `ssh -G` 輸出格式做
一次實際呼叫驗證——只能盲寫 subprocess 呼叫與輸出解析,而 GPT 自己的紀律
「它說『測試過了』都不算證據,自己跑」對我自己一樣適用:寫一個我自己都
無法對真實 `ssh` 二進位跑過一次的解析邏輯,和「盲改」沒有本質差別。這不是
新的方向性顧慮,原樣列進「本輪未處理」,下一輪如果環境裡有 `ssh` 二進位
可以直接做,不需要再重新判斷方向。

### GPT-P0-ENDPOINT-TOCTOU —— 預檢 DNS 解析與 `git ls-remote` 實際連線是兩次獨立解析

**它說什麼**:Python 端的位址解析與 Git/SSH 之後自己做的解析是兩個獨立
步驟,中間沒有綁定,理論上存在 DNS rebinding / round-robin 造成的空窗。

**我查證到的**:成立,程式碼結構確實是這樣——`resolve_host_ips` 只是預檢,
`git ls-remote` 走的是它自己的、完全獨立的解析路徑,兩者之間沒有任何綁定
機制。GPT 給的兩個出口都對:(a) 把實際連線綁定到已驗證的位址,或
(b) 弱化 `remote_observed` 的語意,不再宣稱是強背書。

**為什麼這一輪不做**:兩個出口都超出第 4 節的範圍——(a) 要求接管 Git/SSH/
HTTP 自己的連線行為(例如强制走某個已驗證的 IP,或用 `ProxyCommand`/
`GIT_SSH_COMMAND` 攔截實際連線目標並比對),这是一次不小的傳輸層重新設計,
不是「小而對」的修法;(b) 直接改變 `remote_observed` / `durable-check`
`verdict` 這個既有公開契約對外承諾的強度,是「修法會改變使用者可見行為」,
不是自動迴圈該單方面決定的事。這兩條都對應第 4 節的排除項(大規模重構 /
改變公開行為),也是第 8 節「需要 owner 裁決」的場景,寫進下面。

## 需要 owner 裁決

1. **`GPT-P0-ENDPOINT-TOCTOU`**(這一輪新查證出的問題,列第一次)。
   核心是「`durable-check` 的 `remote_observed: true` 目前只能證明『預檢
   時解析到的位址不是本機』,不能證明『Git 實際連線用的就是那個位址』」。
   三個可能方向,請 owner 選:
   - (a) 接管 Git 的實際連線目標(例如透過 `GIT_SSH_COMMAND` 或
     `-c http.proxy` 之類的機制強制走已驗證的 IP),把 TOCTOU 窗口關掉——
     這是最強的修法,但是傳輸層的重新設計,風險與工作量都不小。
   - (b) 弱化 `remote_observed` 的語意宣稱(文件與欄位命名都要跟著改,
     可能需要新增一個更誠實的欄位名,例如 `preflight_offmachine_hint`,
     不再暗示它是連線本身的強證明)。
   - (c) 維持現狀,但在 docstring / CLI help / `guides/guide-dev-flow.html`
     裡把這個殘留缺口寫得更明顯,不佔用執行邏輯的變更額度。
   我的傾向是 (c) 短期、(a) 長期,但這個判斷本身也需要 owner 確認——
   (a) 的工作量可能大到值得單獨排一輪,不該由自動迴圈自己決定要不要做。
2. **`GPT-P0-WORKTREE-SHARED-STORE`**(連續第 5 輪列出,原樣沿用第 3 輪起
   的三選項與傾向 ③,這輪沒有新資訊)。
