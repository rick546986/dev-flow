## 採納並修好的 finding

### ①[P1] GPT-P1-CURRENT-500 —— CURRENT target 生成在相關性比對之前先套了跟相關性無關的筆數視窗 —— **成立,已修**

**它指的位置**:`memory/agentmem/query.py::_fact_targets()`。

**我查證到的根因**:成立,是「不理論」的真缺陷,連續第 4 輪被回報 NOT FIXED
是對的。`_fact_targets()` 原本是:

```python
for row in store.facts(statuses=truth.LIVE_STATUSES, limit=500):
```

`store.facts()` 的排序是 `ORDER BY recorded_at DESC, fact_id DESC`(見
`store.py:274`)——「最近 500 筆」跟查詢字串的相關性完全無關。函式接下來對
這 500 筆逐一做 entity/fact_key 的精確匹配(`haystack` 命中或
`entity_key`/`fact_key` 直接出現在查詢文字裡)。只要一個 project 累積超過
500 筆 live fact,而唯一正確的 CURRENT 答案剛好比 500 筆別的 fact 舊,它
在比對開始之前就已經被砍掉——`_current()` 會因為 `_fact_targets()` 回空
列表而找不到 fast path,退回模糊檢索,最後回 `NEEDS_VERIFICATION` 而不是
`OK`。整段砍法對呼叫端完全靜默,沒有任何錯誤或警告。

這跟 GPT 說的完全一致:「這不是效能取捨,是把資料列上限用在相關性判定
之前」——`store.facts()` 的 `limit` 語意本來就是給**整檔取代**(見
`sync.py::promote_entity_facts` 的 docstring,同一份程式碼庫已經有
`durable-full-replace-no-window` 這條姊妹不變量)或**已排序過的探索式檢索**
用的視窗,不是給精確匹配用的過濾器。

**「舊實作下真的紅」的證據**(`test_query.py::ExecutionTest::
test_current_target_beyond_row_window_still_resolves`,新增 1 案,舊實作下
實紅):

```
AssertionError: 'NEEDS_VERIFICATION' != 'OK'
```

治具:`ExecutionTest.setUp()` 已經記了一筆 `database.lab-order.current_table
= lab_order`(`VERIFIED`,`recorded_at` 是 setUp 執行當下的 wall clock);
新測試在那之後插入 500 筆不相關的 `filler.filler-{i}.noise = value`
(`CANDIDATE`,`recorded_at="2030-01-01T00:00:00Z"`,刻意設成比 setUp
那筆新,確保 `ORDER BY recorded_at DESC` 排序下它們全部排在 setUp 那筆
之前)。舊實作下,`store.facts(limit=500)` 只會撈到這 500 筆 filler,
setUp 那筆被擠出視窗,對它的精確查詢(「目前 lab-order 的 current_table
是什麼?」)直接查不到 fast path,回 `NEEDS_VERIFICATION`——這正是 GPT 給的
情境:「Insert >500 live facts such that the only exact CURRENT target is
ordered outside the first 500 rows.」

**修法**:`_fact_targets()` 的 `store.facts(...)` 呼叫改成 `limit=None`,
不再套前置視窗;函式本身的比對邏輯(haystack / entity_key / fact_key 精確
命中)完全不動——這不是模糊排序後加視窗,一開始就不該有視窗。

**不動的部分**:`_search()`(模糊、多通道 RRF 排序的探索式檢索)完全不受
影響——那支本來就是先排序、再依 `limit` 參數截斷,截斷點在相關性排序
**之後**,是 GPT 自己說的「安全的優化」,不是這條 finding 的對象。

**GPT 給的回歸測試**,核對:「Insert >500 live facts such that the only
exact CURRENT target is ordered outside the first 500 rows. Query that
exact entity/fact and require it to resolve normally. The test must fail
if row insertion/recording order alone can hide the answer.」——**已覆蓋**
(見上方治具),而且已經在舊實作下驗過真的紅,不是憑印象寫的通過測試。

**萃取**:1 筆進 durable —
`knowledge/invariants/relevance-cap-must-come-after-not-before-exact-match`
(精確匹配的候選產生不得有前置筆數視窗;跟 `durable-full-replace-no-window`
是同一個根因家族在讀取端的對應版本——寫入端與讀取端都不得用「最近 N 筆」
這個跟相關性無關的排序當過濾器)。走 `dev-talk`(propose → confirm →
checkpoint → end),`promoted: 1`,`revisions: 0`。

### GPT-P0-REMOTE-ATTESTATION-UNSOUND(前身 GPT-P0-LOCAL-IP-INVENTORY-FAILOPEN 的重新定性)—— 這一輪還是沒做,原樣沿用上一輪「需要 owner 裁決」

**它說什麼**:上一輪修的「本機介面位址列表為空」只是這個問題的一個窄子案例;
「非空但不完整」的 `_local_machine_ips()` 仍然可能讓 `ip_is_offmachine` 誤判

架構問題的另外兩種表現。GPT 挑戰上一輪 Claude 傾向的「短期 (c) 文件化、
長期 (a) 接管連線」排序,主張應該立刻 fail closed(選項 1)或改欄位語意
(選項 2),不接受「文件化殘留缺口」當短期方案。

**我查證到的**:程式碼現況與 GPT 描述一致,親自重讀
`memory/agentmem/identity.py::ip_is_offmachine()` /
`memory/agentmem/sync.py::_observe_remote()` 逐行確認 ——
`_observe_remote()` 現在確實只擋空集合(上一輪修的那個案例),非空但不完整
的 `local_ips` 仍然只靠 `raw_ip not in local_ips` 這個負向測試判定
off-machine,而 `_local_machine_ips()` 的 docstring 自己就寫明只有兩種
best-effort 探測手法、不保證完整。GPT 給的具體反例(機器有
`{10.0.0.20, 192.168.50.8}` 兩個介面,探測只拿到 `{10.0.0.20}`,remote
恰好解析到 `192.168.50.8`)在目前程式碼下確實會被誤判成 off-machine 而
PASS——這不是我用測試重現的,是純讀程式碼邏輯推導,但邏輯鏈完全站得住。

**為什麼這一輪還是沒動程式碼**:GPT 給的兩個「誠實契約」選項——(1)
沒有強證據就 fail closed 到 `REMOTE_UNVERIFIED`,或(2)拆分並重新命名

- 選項 (1) 會讓**現有測試**裡合法的正向案例(`test_off_machine_remote_

  passes`)理論上也失去 PASS 的資格,因為目前系統本來就沒有「transport-
  specific 正向證明端點」的機制——這不是修一個邊角案例,是把整個
  `remote_observed` 判定從「負向測試」改成要求「正向證明」,沒有正向證明
  來源時等於讓這個功能大部分時間都回 `REMOTE_UNVERIFIED`,是行為上的
  倒退,不是「小而對」的修法。
- 選項 (2) 是重新命名/拆分一個目前程式對外(CLI 輸出、下游 Stage 6)已經在

依第 4 節紀律與第 8 節「修法會改變公開 API 或使用者可見行為,而不只是修正
錯誤」→ 不動程式碼,列進下面「需要 owner 裁決」。這是上一輪(`20260821-
0608`)已經列出的同一個裁決項,這輪 GPT 沒有提供新的偵測手段(我在上一輪

## 需要 owner 裁決

   - (b) 弱化 `remote_observed` 語意,拆成 `remote_ref_matches` +
     `preflight_not_known_local` 之類更誠實但較弱的欄位,`durable-check`
     的 verdict 不再暗示它是連線本身的強證明。
   - (c) 維持現狀,把殘留缺口寫得更明顯(docstring / CLI help /
     guide),不佔用執行邏輯的變更額度。
   GPT 這輪明確主張不接受 (c) 當短期方案,理由是「一個已知的 false-
   positive 路徑本身就是 barrier 的正確性缺陷,文件不能讓假證明變安全」。

   `durable-check` 現有正向案例（真的離開本機的 remote）要不要在拿到更
   強的 attestation 機制之前先降級成 `REMOTE_UNVERIFIED`,這是會改變現有
   行為的產品層決策,不該由自動迴圈單方面選。
