## 採納並修好的 finding

### ①[P0] durable 現況檔在 1000 筆處被靜默截斷 —— **成立,已修,而且比它說的更糟**

**它指的位置**:`memory/agentmem/sync.py::promote_entity_facts()`。

**我查證到的根因**(不是照抄):

它說的是「`limit=1000` 會在 entity 超過 1000 筆 durable-eligible fact 時截斷」。
查證後那個描述**低估了觸發條件**。原本的呼叫是:

```python
facts = [f for f in store.facts(entity_type=..., entity_key=..., limit=1000)
         if f["status"] in _FACT_STATUS_DURABLE]
```

`limit` 進的是 SQL `LIMIT`(`store.py:274`,`ORDER BY recorded_at DESC,
fact_id DESC`),而 status 過濾在 **Python 端、視窗之後**。所以視窗算的是
「這個 entity 的**所有** fact 列」,不是「durable-eligible 的那些」。後果:

- 真正的邊界是 **1000 筆任意狀態的 fact**,不是 1000 筆現行 fact。
- 極端情況只需要 **1 筆現行 fact**:1000 筆較新的 `SUPERSEDED`(正常的更正
  歷史,不是病態資料)就能把唯一的現況擠出視窗。

而傷害來自它跟 `write_state()` 的組合:`write_state` 是**整檔取代**(這是對的,
supersede 語意住在整組 fact 上)。取代 + 前 N 筆 = **刪掉視窗外的那些**。它們
上一輪已經在檔裡、也已經 `durable=1`,這一輪的取代把它們從檔案裡拿掉,而 local
那幾列仍然聲稱「我就是 `.dev-flow/` 裡的那份」。`durable-check` 於是判 PASS 在
一個不完整的鏡射上 —— 這正是本專案在修的同一個錯的另一個落點:**在耐久性真正
建立之前就把狀態往前推**。

「舊實作下真的紅」的證據(`memory/tests/test_durability_barrier.py::DurableStateIsCompleteTest`,4 案):

| 測試案 | 舊實作下的實際輸出 |
|---|---|
| `test_every_current_fact_reaches_the_durable_state_file` | `1000 != 1250` |
| `test_destructive_rebuild_returns_every_current_fact` | `1000 != 1250`(砍掉 SQLite、只從 `.dev-flow/` 重建) |
| `test_superseded_neighbours_cannot_push_a_current_fact_out` | `'live00000' not found`(1 筆現行 + 1200 筆較新的 SUPERSEDED) |
| `test_no_fact_is_marked_durable_without_being_in_the_file` | 300 筆 `first000xx` 標著 `durable=1` 但檔案裡沒有 |

第四案第一版寫成單輪就綠了(單輪內 `durable=1` 只標真的寫進去的那些),改成
兩輪(900 筆 → promote → 再加 400 筆較新的 → promote)才暴露跨輪的假宣稱。
記在這裡是因為它說明了這個缺陷為什麼一直沒被發現:**它只在第二次整檔取代時
才現形**。

**修法**:`store.facts()` 支援 `limit=None`(不加 `LIMIT` 子句),
`promote_entity_facts()` 改成 `statuses=sorted(_FACT_STATUS_DURABLE),
limit=None` —— status 下推到 SQL、視窗拿掉。沒有選 GPT 提的「分頁撈完」:
`write_state()` 本來就要拿到完整 list 才能整檔取代,分頁進 list 的記憶體足跡
與一次查完相同,只是多一層可以寫錯的迴圈。也沒有選它的第二個選項(訂一個
per-entity 上限並在寫入時拒絕)—— 那是把一個資料遺失缺陷換成一個產品限制,
而這個限制沒有任何使用者需求支持。

`store.facts()` 其他呼叫端的預設 `limit=200` 沒動 —— 要視窗的呼叫端自己傳,
不變的是「整檔取代的 writer 不得有視窗」。

**新守衛(含變異驗證)**:`check-memory-architecture.sh` 新增
「durable 現況檔整檔取代時不設筆數視窗、status 下推到查詢」,
negative case `MEM-22` 把 `limit=1000` 放回去 → 守衛紅(已驗)。

### ②[P1] `durable-check` 用本機追蹤 ref 當遠端證據 —— **成立,已修**

**它指的位置**:`memory/agentmem/sync.py::durable_check()` 第②項。

**我查證到的根因**:原本是

```python
upstream = _git(repo_root, "rev-parse", "--abbrev-ref", "@{upstream}")
remote_head = _git(repo_root, "rev-parse", upstream)   # ← origin/<branch>
```

`origin/<branch>` 是**本機快取**,只有 `fetch`/`push` 才會更新。所以這一關唯一
要回答的問句(「記憶離開這台機器了嗎」)拿的是一份沒有離開這台機器的證據。別台
機器 force-push 或刪掉那個 branch 之後,它會替一個伺服器上已經不存在的 commit
背書。

**「舊實作下真的紅」的證據**(`DurableCheckTest`,4 案):

| 測試案 | 舊實作下的實際輸出 |
|---|---|
| `test_stale_tracking_ref_cannot_prove_remote_durability` | `'PASS' != 'FAIL'`(bare remote 的 branch 被 `update-ref` 換掉、本機刻意不 fetch) |
| `test_unreachable_remote_fails_closed` | `'PASS' != 'FAIL'`(遠端目錄整個刪掉仍判 PASS) |
| `test_local_only_is_explicit_and_says_so` | `TypeError`(沒有 `local_only` 參數) |
| `test_remote_observed_is_recorded_on_a_real_pass` | `KeyError: 'remote_observed'` |

**修法**:新增 `_observe_remote()`,用 **`git ls-remote`** 問遠端本身。三個
刻意的選擇:

1. **不用 `fetch`**(GPT 建議的做法):判定不該順手改本機的 ref —— 判定改變被
   判定的狀態,下一次判定就不是獨立的。`ls-remote` 是唯讀的。
2. **remote / ref 從 `branch.<name>.remote` 與 `.merge` 讀**,不從 `origin/xxx`
   這個字串切:branch 名字本身可以有 `/`,切錯會問錯 ref 然後判 FAIL(一個假
   FAIL 一樣是壞的判定)。
3. **問不到遠端一律 FAIL**(新代碼 `DURABLE_REMOTE_UNVERIFIED`)。離線要放行
   請明確 `durable-check --local-only`,而那條路回傳 `remote_observed=false`
   —— 可以放行,但**不得聲稱驗過遠端**。

判定結果多一個欄位 `remote_observed`,README §16.9 那條清單同步更新。

**新守衛(含變異驗證)**:「durable-check 向遠端本身查證 HEAD」,negative case
`MEM-24` 把它換回 `rev-parse upstream` → 守衛紅(已驗)。

### ③[P2] 同 `event_id` 不同內容被靜默丟棄 —— **成立,已修**

**它指的位置**:`memory/agentmem/durable.py::append_events()`。

**我查證到的根因**:上一輪引入的去重是 `if event_id in seen: continue`。那個
推論(「id 在檔裡」⇒「這筆寫過了」)只有在 **id 真的決定內容**時成立。推導 id
的來源(`candidate_id` / `revision_id`)撞號、或推導規則有瑕疵時,第二筆(內容
**不同**的那筆)會永遠不存在,而呼叫端拿到成功 —— 又是一次靜默失憶,而且這次
是上一輪的修法自己引入的。

**「舊實作下真的紅」的證據**(`test_durable.py`,2 案,皆 `DurableError not
raised`):`test_same_event_id_with_different_content_fails_loud`、
`test_same_event_id_twice_in_one_batch_with_different_content`。

**修法**:`_existing_events()` 從回傳 id 集合改成回傳 `{event_id: 正規化內容}`
(新的 `_canonical()`,`sort_keys=True`),`append_events()` 撞號時比內容,不同
就 `raise DurableError`。順手修掉一件 GPT 沒提的:原本邊算邊寫,撞號在第二個
檔才發現時第一個檔已經寫出去了 —— 改成**先把整批算完(含撞號判定)才動任何
一個檔**,部分寫入的批次沒人能複驗它做到哪裡。

**新守衛(含變異驗證)**:「event append ... + 撞號 fail closed」。第一版守衛
釘的是 `"DurableError" not in ap_code` —— **變異驗證直接抓到它是假守衛**:
同一個函式裡「缺 event_id 就拒收」那條路也提供那個字串,把守衛餵飽了
(`MEM-23` 預期 fail 實得 pass)。改成釘 `seen[event_id] !=` 這個**機制**
之後才真的紅。記在這裡是因為它是「沒紅的守衛等於沒寫」的一個現成例子。

## 給 GPT 的下一輪輸入

### 最該被挑戰的設計決策(1–2 條)

1. **`durable-check` 用 `ls-remote` 而不是 `fetch`,而且不快取。** 我的理由是
   「判定不該改變被判定的狀態」。值得挑戰的點:`ls-remote` 只證明**那個 ref
   現在指到我的 commit**,不證明 object 真的完整存在於遠端(理論上 ref 存在而
   object 不完整);`fetch` 會真的把 object 拉過來因而證明得更多。我認為那個
   差異在 Git 的推送語意下不可能發生(push 成功才會有那個 ref),但如果你能
   構造出反例,那我這個選擇是錯的。
2. **①的修法選了「不設上限」而不是「訂一個 per-entity 上限」。** 值得挑戰的
   點:一個 entity 累積到數萬筆 fact 時,`promote_entity_facts` 會把它們全部
   讀進記憶體並整檔重寫,而那個成本沒有任何上界。我認為正確的解不是把上限加
   回來(那是資料遺失),而是「一個 entity 累積數萬筆 fact」本身是 supersede
   語意沒有正確收斂的徵兆 —— 但我沒有測試證明這一點。

### 我不打算改的方向與理由(省下你重複建議)

- **worktree/shared-DB 隔離**:已升級成「需要 owner 裁決」並附上我的技術意見與
