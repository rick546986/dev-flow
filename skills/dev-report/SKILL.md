# dev-report — 缺陷回報(採用現場 → 母版)

你唯一的任務:把「這個專案踩到的 dev-flow 母版缺陷」整理成**去識別化**的回報材料,
寫進 `.devflow/reports/<代號>.md`,完整顯示給使用者確認。**不自動開 issue、不傳送
任何東西** —— 貼到哪裡、貼不貼,由人決定。

## 為什麼是這個形狀(owner 已裁決,不要改方向)

- **dev-flow 是 public repo**(Pages 也開著)。採用專案是公司的 —— 專案名、路徑、
  規格內容一旦進 public issue 就是公開的。所以走「產出去識別化回報檔,人工貼」。
- **去識別化在撰寫當下就做**,不是寫完再篩 —— 識別資訊一旦落檔,「之後再刪」
  永遠會漏。
- owner 固定時間處理回報,不需要自動指派或通知。

## 產出:同一份材料,兩個區塊,一個檔案

寫到 **`.devflow/reports/<代號>.md`**(代號 = 小寫英數連字號,描述缺陷不描述專案)。
⚠️ 這個位置在 `.gitignore`(`.devflow/`)內 —— 回報檔是暫存物,貼完即可刪,
不進採用專案的版控。若執行守衛武裝中(`.devflow/` 禁寫),先 `devflow-exec.sh stop`
或換一個未武裝的 session 再產出。

```markdown
# 回報:<一句缺陷>

## A. 給 issue 貼的(現象/重現/影響/環境)
- 現象:<守衛/檢查的固定輸出原文 + 錯在哪>
- 重現:<用母版自己的檔案路徑與最小輸入重現;逐步指令>
- 影響:<會誘導什麼錯誤行為/擋住什麼>
- 環境:plugin <版本>、契約 <版本>

## B. 給派工單貼的(可直接進 notes/dispatch-*.md)
| 位置 | 一句缺陷 | 具體失敗情境 | 建議修法方向 |
|---|---|---|---|
| <母版檔案:行號> | <一句> | <什麼輸入/狀態會錯> | <一句方向,不是實作> |
```

## 去識別化規則:白名單,fail-closed

**只有下列東西可以直接保留**(全部是「母版的」或「泛化後的」):

| 保留 | 例 |
|---|---|
| 母版自己的檔案路徑與行號 | `scripts/check-spec-gate.sh:85` |
| 正則 pattern、字元碼、程式碼片段(母版的) | `[^:：\n]*[:：]`、`0x3a` |
| exit code、檢查名稱、守衛輸出的固定文字 | `❌ C1 每個 S 都有觀測欄` |
| plugin 版本、契約版本 | `3.20.4` / `2.0.0` |
| 泛化後的結構 | `<專案根>`、`<slug>`、`R-1`、`S-1.2`、`T-3` |
| 數量 | 「16 個 S 裡有 13 個被誤判」 |

**其餘一律不得自動帶入**,包括但不限於:專案名、repo 名、絕對路徑、分支名、
commit SHA、業務欄位的實際文字(GIVEN/WHEN/THEN 的內容、Owner Call 的理由)、
人名、系統名、資料庫/表名。

**需要那些才說得清楚時 → 停下來問使用者要不要帶、帶哪一段**,不要自己決定。
把業務文字改寫成泛化例(`<欄位A>`、`<系統B>`)通常就夠說清楚了。

⚠️ **不得建立公司名稱黑名單來過濾** —— 那份清單本身就是洩漏,而且會進 public repo。

## 兩層防線(缺一不可;不得宣稱「hook 上了就安全」)

1. **機械層(每次都跑,擋得死)**:`devflow-report-guard` hook 在你每次寫
   `.devflow/reports/*.md` 之後掃**結構性**識別特徵 —— 絕對路徑、git SHA、email、
   內網位址、分支名、**不存在於母版 repo 的檔案路徑**(最有價值的判準:不需要知道
   任何公司名,只問「這路徑母版有嗎」)。命中 → 擋回並列出行號,先去識別化再寫。
2. **語意層(只有人看得出來)**:公司名、系統名、表名、業務術語**沒有結構特徵**,
   hook 看不出來。靠上面的白名單紀律 + 下面的人工確認。

## 產出前必須做的最後一步(不可省略)

把整份回報檔**完整顯示**給使用者,並附這一行:

> 「以下內容將被貼到 **public** repo,請確認沒有不該公開的東西。」

**使用者沒明確說可以,就不算完成。** 之後提醒:B 區塊可直接貼母版
`notes/dispatch-*.md`,A 區塊貼 issue;貼完可刪回報檔。
