A 登入即時查

dashboard 載入時 API 即時查 expiring 合約 優:零新 infra、實作最小 劣:每次載入查一次;無主動推播 依據:`1-discussion.md:18` 現有 dashboard 已有空白卡片區;`:116` explore 記「dashboard 是最低成本呈現面」。成本 `[Assumption]`

B nightly cron + 通知表

排程掃描寫入 notifications 表 優:可擴充 email;查詢便宜 劣:要新增 cron 進程 + 新表 依據:`1-discussion.md:68` Non-Goals 記 email 之後再議;`:116` 現況無任何排程機制。成本 `[Assumption]`

C MQ 事件驅動

合約異動發事件,消費者判斷到期 優:即時、最可擴充 劣:引入 MQ = 新 infra,violates constraint 依據:`1-discussion.md:80` Constraints 明列「不引入新 infra」。成本 `[Assumption]`

背景

Rationale 量級小(8k 筆,索引查詢 <50ms)、需求只到「看得到」,即時查是最短路徑;service 抽象保住升級路。

風險 - 查詢慢拖累 dashboard → prototype 前先 EXPLAIN 驗證;超過 100ms 就加覆蓋索引。 - UI 形式不確定(badge? 卡片?)→ 交給 3-prototype 用 variants 挑。

未採 - B:本期不做 email,通知表沒有消費者,先做是浪費。 - C:8,000 筆量級用 MQ 是 overkill,且違反「不引入新 infra」約束。
